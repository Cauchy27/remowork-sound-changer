## 1. 7軸の詳細と質問バンク

判断軸は次の順序で固定する。各軸で使う問いかけは例示であり、対象に応じて言い換えてよいが、軸の順序と意味は変更しない。

### 1.1 目的

**確認すること**: 誰のどの問題を解き、何を達成する成果物か。

- 「これ、結局だれが読んで何に使うもの？」
- 「目的が1個に絞れる？　複数の目的が混ざって、どっちつかずになってない？」
- 「この成果物がなかったら、誰がどう困るの？」
- 「（remowork-sound-changer固有）着信音・通知音のカスタマイズって、Remoworkでの応対スピードや対応品質にどう効くの？」

### 1.2 意思決定

**確認すること**: 読み手や利用者が、これを受けて何を正しく決められるか。

- 「これ読んだ人、次に何を決められるの？」
- 「決めるのに必要な情報、ここに全部揃ってる？」
- 「情報は多いけど、結局何が言いたいのか一言で言える？」

### 1.3 前提

**確認すること**: 事実、未確定事項、仮定が区別され、根拠へ辿れるか。

- 「それ、確定してること？　それとも希望的観測？」
- 「前提条件、どこかに書いてある？　それとも頭の中にしかない？」
- 「この数字・この主張、どこから来たの？」
- 「（remowork-sound-changer固有）本番（remowork.biz）とステージング（stage.remowork.biz）で挙動が違う前提、ちゃんと分けて考えてる？」

### 1.4 因果

**確認すること**: 主張から結論、施策から効果、操作から結果が論理的につながるか。

- 「その結論、どの根拠からつながってる？」
- 「Aをやったら本当にBになるの？　間に飛躍ない？」
- 「相関と因果、ごっちゃになってない？」

### 1.5 矛盾

**確認すること**: 同一成果物内、正本、実装、運用の間で約束が食い違っていないか。

- 「こことあそこ、言ってること違わない？」
- 「仕様書と実装、ちゃんと一致してる？」
- 「前に決めたことと、今回のこれ、矛盾してない？」

### 1.6 業務上の代償

**確認すること**: 誤解、手戻り、誤発注、誤実装、停止、責任の空白を生まないか。

- 「これを誤解したら、現場で何が一番困る？」
- 「これが原因で手戻りが起きるとしたら、どこ？」
- 「誰の責任か分からなくなる瞬間ない？」
- 「（remowork-sound-changer固有）音が鳴らない・誤って停止する不具合が起きたら、着信見逃しみたいな業務事故につながらない？」

### 1.7 次アクション

**確認すること**: 誰が、何を、いつ、どの条件で行うかが判断できるか。

- 「次に動くのは誰？　いつまでに何をするの？」
- 「条件分岐がある場合、どっちに転んでも次の一手が分かる？」
- 「『検討する』で止まってて、実は誰も動けない状態になってない？」

## 2. レビュー時の4観点（要約表）

エージェント定義の判断軸を、指摘作成時にすばやく参照するための要約。

| 観点 | 確認内容 | 対応する軸 |
|---|---|---|
| 目的・意思決定 | 誰の何を解き、読み手が何を正しく決められるか | 1.1, 1.2 |
| 根拠・因果 | 主張の根拠へ辿れ、前提から結論まで論理がつながるか | 1.3, 1.4 |
| 矛盾・業務代償 | 正本や実装との食い違いが、どの誤解・手戻り・損失を生むか | 1.5, 1.6 |
| 次アクション・最小修正 | 誰が次に動けるか、最小差分で本質的な欠陥を直せるか | 1.7 |

## 3. 出力フォーマットの厳密な定義

エージェント定義の「出力フォーマット」節が正本。ここでは `validate_report.py` が検証する構造要件を明文化する。

```markdown
# 本質ギャルレビュー

**対象**: {対象}
**review-iteration**: {review-iteration}
**確認した正本**: {正本パス。なければ「特定できず」}
**一言結論**: {快活かつ端的な結論}

## 指摘

| 指摘ID | 優先度 | 対象箇所 | 根拠 | 本質的影響 | 最小修正 |
|---|---|---|---|---|---|
| GYARU-{review-iteration}-001 | [MUST] | file:line | 確認した事実 | 誤る意思決定や業務上の代償 | 最小の修正案 |

## ファクトチェック受け渡し

- 指摘件数: {N}
- 全指摘ID: {カンマ区切りID一覧。0件なら「なし」}
```

### 構造要件

| # | 要件 |
|---|------|
| 1 | 1行目が `# 本質ギャルレビュー` であること |
| 2 | `## 指摘` と `## ファクトチェック受け渡し` の見出しがそれぞれ1回ずつ存在すること |
| 3 | 指摘表のヘッダーが `指摘ID / 優先度 / 対象箇所 / 根拠 / 本質的影響 / 最小修正` の6列であること |
| 4 | 指摘IDは `GYARU-{review-iteration}-{3桁連番}`（例: `GYARU-1-001`）であり、`{review-iteration}` が実行時の値と一致すること |
| 5 | 優先度は `[MUST]` / `[SHOULD]` / `[NIT]` / `[Q]` のいずれかであること |
| 6 | 指摘が1件以上ある場合、指摘表の各セルが空でないこと |
| 7 | 指摘が0件の場合だけ、表の直後に「本質的な指摘なし。目的、意思決定、前提、因果、矛盾、業務上の代償、次アクションを確認済み。」と記録すること |
| 8 | 「ファクトチェック受け渡し」の指摘件数が指摘表の行数と一致し、全指摘IDが指摘表のIDと過不足なく一致すること |
| 9 | 区切り行は各セルをハイフンちょうど3つで書くこと（上と下の例の2行目のとおり。セル前後の空白は可。コロン付きの `:---` や4つ以上の `------` は不可）。区切り行はヘッダー行の直後に置く |
| 10 | 表の行は行頭からパイプ記号で始めること（字下げした行は指摘として数えられない） |
| 11 | 指摘ID（表の1列目と「全指摘ID」）をバッククォートで囲まないこと（表の1列目で囲んだ行は指摘として数えられず、件数の不一致か、0件扱いで定型文が無いという ERROR になる。「全指摘ID」で囲むと `invalid ID in 全指摘ID` の ERROR になる） |
| 12 | 優先度はタグを角かっこごと書くこと（`MUST` ではなく `[MUST]`） |
| 13 | セルの中にパイプ記号を書かないこと（バックスラッシュでエスケープしても列が割れる）。必要なら `&#124;` か言葉で書く |
| 14 | 指摘が0件でも、ヘッダー行と区切り行は残し、データ行を書かずに、その後へ要件7の定型文を置くこと（下の例） |

指摘0件のときの「指摘」節:

```markdown
## 指摘

| 指摘ID | 優先度 | 対象箇所 | 根拠 | 本質的影響 | 最小修正 |
|---|---|---|---|---|---|

本質的な指摘なし。目的、意思決定、前提、因果、矛盾、業務上の代償、次アクションを確認済み。

## ファクトチェック受け渡し

- 指摘件数: 0
- 全指摘ID: なし
```

### 手動適用の記録

独立サブエージェントを起動できず、実行役が同一セッションで手動適用した場合（SKILL.md「Cursor での手動実行手順」）は、`**一言結論**` 行の直後に次の1行を足す。`validate_report.py` はこの行を検査しない。

```markdown
**独立性**: 同一セッションで手動適用（{実行役のツールとモデル}。サブエージェントを起動できなかった理由: {理由}）。独立性は低下している。
```

呼び出し元へ返すとき（SKILL.md Instructions 手順4・5）も同じ旨を書く。`code-review` 経由なら、呼び出し元は統合結果の独立性の申告（[review-matrix.md](../../docs/review-matrix.md) の「独立性の申告」）へ写す。独立サブエージェントや別モデルで実施したことにしない。

## 4. 指摘の付け方の注意

- 表記ゆれ、余白、好みだけの言い換えは、目的達成を阻害しない限り指摘しない（表層デザイン単独の指摘は design-critique の領分）
- 技術詳細（言語・フレームワーク・セキュリティ実装）そのものへの指摘は主務外。7軸に沿った本質的な影響として言い換えられる場合だけ指摘に含める
- 根拠を確認できない事項は断定せず、優先度タグは常に `[Q]` を使い、根拠または最小修正のセルに「要追加検証」の旨を明記する
- 強い口調を権威として使わず、最終判断は `code-review-fact-check` の4判定（妥当/部分的に妥当/過剰/事実誤認）に委ねる
