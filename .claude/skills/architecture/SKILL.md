# ADR（意思決定記録）スキル

## 使用宣言

```text
[architecture スキルを使用します]
モード: 記録（新しい判断を残す） / 参照（既存の確定判断を読む）
参照: .claude/skills/architecture/SKILL.md
```

## 概要

判断が口頭・チャット・タスクコメントに散在して埋もれることを防ぐ。正本は Git 管理された `.docs/adr/` の ADR であり、**実装の根拠になるのは status が「確定」のレコードだけ**である。

対象は技術選定に限らない。仕様解釈・データモデル・業務ルール・採否・フェーズ分けなど、後から「なぜそうなっているのか」を問われる判断はすべて同じ契約で記録する。

詳細なテンプレート・記入例・移行手順・サブエージェント活用は [reference.md](./reference.md) を参照する。

## ADR の契約

### status と実装根拠

| status | 意味 | 実装根拠 | 本文の編集 |
|---|---|---|---|
| 検討中 | 承認待ち。まだ決定ではない | 不可 | **可**（確定するまで書き直してよい） |
| 確定 | 承認済みで、現在有効な判断 | **可** | **不可** |
| 置換 | 後続の確定 ADR に置き換えられた | 不可 | 不可（置換先を追記するのみ） |
| 失効 | 前提が消滅して効力を失った | 不可 | 不可（失効理由を追記するのみ） |

**遷移は一方向。** 検討中 → 確定 / 置換 / 失効、確定 → 置換 / 失効。逆行させない。確定した内容を変えたくなったら、本文を書き換えず**後続 ADR を作って旧レコードを置換**する。判断が変わった事実そのものが記録の一部である。

### 証跡

- 出典は**1件以上必須**。status を問わず空にしない
- 確定にするときの出典は、**後から第三者が参照できる記録**を指すこと。PR・Issue・タスクのURL、チャットのメッセージリンク、会議記録などが該当する
- **AIとの会話を唯一の証跡にしてはならない。** 会話は Git に残らず、後から独立に検証できない
- 会話で決まった場合は、その内容を PR 説明・タスク・チャットへ書き出し、**それに対する人間側の応答（承認返信・承認スタンプ・マージ承認など）を受け取ってから**、その応答を出典にする。**AI が自分で書き出しただけのものを出典にしてはならない。** 書き出しと引用を同一の主体が完結できてしまうと、証跡は自己参照になり承認の意味を失う
- リンク先は削除・編集されうる。**URL に加えて、承認内容を1行で要約併記する**
- 通常の技術判断は PR レビューを承認の証跡として扱ってよい。組織外・チーム外へ影響する業務判断だけ、固定URLやメッセージIDを明示する

### 粒度

**1レコード1論点。** 複数の論点を1つの ADR に束ねない。束ねると、1項目を変えるだけでレコード全体を置換する必要が生じ、履歴が読めなくなる。

判断に迷ったら「この1件だけを後から覆せるか」で切る。覆せない粒度なら分割する。

## ワークフロー

### Phase 0: 参照（判断の前に必ず行う）

実装中に仕様解釈・採否・API・データモデル・業務ルール・画面導線を判断する直前に、このスキルへ入る。

**対象外（記録しない）**

- 既に確定した判断を適用するだけの機械的な実装・テスト
- **後から容易に覆せる判断**。変数名・小さなAPI項目の選び方・ローカルな実装方式など、変更コストが小さく影響が閉じているもの。覆すコストが低い判断まで ADR にすると、記録が増えすぎて肝心の判断が埋もれる

判断に迷ったら「これを半年後に覆すとき、何人がどれだけ動くか」で測る。自分ひとりで数時間なら記録しなくてよい。

1. `Glob` / `Grep` で `.docs/adr/` を検索し、関連する既存 ADR を洗い出す
2. **status が「確定」のものだけ**を根拠として読む。検討中・置換・失効は経緯であり根拠にしない
3. 既存の確定判断で答えが出るなら、それを適用して進む。新しい記録は作らない
4. **矛盾がある、必要な判断が検討中、または未登録の場合は、推測で選ばない。** 判断が要る旨を明示してユーザーへ確認する。確認が取れるまで、その判断に依存する実装だけを保留し、独立して進められる作業は続ける

### Phase 1: 問題・背景の整理

1. 解決すべき課題・制約を明確化する
2. 意思決定の対象スコープを特定する。「この決定で何を変えるのか」を1文で定義する

### Phase 2: 選択肢の列挙と比較

技術選定・アーキテクチャ決定では、現実的な選択肢を2〜5案（採用案・却下案・現状維持を含む）列挙し、比較マトリクスを作る。評価軸は3〜5項目に絞る。軸の例と書式は [reference.md](./reference.md)。

仕様解釈・業務ルールなど**選択肢が自然に2案以上にならない判断では、比較マトリクスは省略してよい。** ただし「他にどうすることもできたか（捨てた案）」は必ず1行以上書く。捨てた案が無いと、後から再検討するときに何を検討済みなのかが分からない。

### Phase 3: 意思決定と理由の記述

1. 採用案と選定理由を具体的に書く
2. 却下案の棄却理由を明記する
3. 再検討すべき条件（前提が変わったら覆る条件）を列挙する

### Phase 4: 影響範囲の評価

既存システムへの影響（破壊的変更の有無）、移行コストと手順、リスクと軽減策を記述する。

### Phase 5: 記録

1. [reference.md](./reference.md) のテンプレートで文書を作成する
2. `.docs/adr/YYYYMMDD-{short-title}.md` に保存する（1レコード1ファイル）
3. 承認が得られるまでは status を「検討中」にする。承認を得てから「確定」へ上げ、そのとき出典に追跡可能な記録を入れる
4. 既存 ADR を置き換える場合は、旧レコードの status を「置換」にし、本文末尾に置換先の ID を追記する

5. `scripts/check-adr.py` があれば実行し、契約違反がないことを確認する

```bash
python3 scripts/check-adr.py .docs/adr
python3 scripts/check-adr.py .docs/adr --base origin/main   # 確定レコードの改変も検査
```

この checker は status の値・必須キー・出典の形式・置換先の有無・失効理由の有無といった**答えが一意に決まる項目だけ**を見る。判断が妥当か、証跡の中身が本当に承認かは見ない。そこは人間のレビューの領分である。

ADR が増えて一覧が必要になったら `.docs/adr/README.md`（または `index.md`）を作る。件数が少ないうちは `Grep` で足りるため、一覧の維持を義務にしない。

## Checklist

- [ ] 判断の前に `.docs/adr/` を検索し、確定済みの判断を確認した
- [ ] 矛盾・未登録・検討中の判断を推測で埋めず、ユーザーへ確認した
- [ ] この判断は ADR に値する重要度か確認した（後から容易に覆せる判断を記録していない）
- [ ] 1レコード1論点になっている（複数の論点を束ねていない）
- [ ] 出典を1件以上記録した
- [ ] 確定にする場合、出典が後から第三者に参照できる記録を指している（AI会話のみになっていない）
- [ ] 確定にする場合、**その記録に人間側の応答が含まれている**（AI が書き出しただけのものを出典にしていない）
- [ ] 出典に URL だけでなく、承認内容の1行要約を併記した
- [ ] 捨てた案とその棄却理由を書いた
- [ ] デメリット・リスク・代償を正直に書いた
- [ ] 再検討トリガーとなる条件を明記した
- [ ] status を設定した（承認前は「検討中」）
- [ ] 確定済みレコードの本文を書き換えていない（変更は後続 ADR による置換で行った）
- [ ] `.docs/adr/` に命名規則どおり保存した
- [ ] `scripts/check-adr.py` があれば実行し、違反0を確認した

## サブエージェント活用

影響範囲が大きい技術選定では `solution-architect` / `cto` / `tech-lead` の3視点を並列でレビューさせ、Phase 2 の比較精度を上げる。設定値の調整や小規模な入れ替えでは単独進行でよく、無条件に委託しない。

起動手順とプロンプト雛形は [reference.md](./reference.md)。記述規約: [agent-invocation-patterns.md](../../docs/agent-invocation-patterns.md)

## ローカライズ

`post-import-setup`（新規導入時）と `template-rollout`（横展開時）で、各プロジェクトに合わせて次を確認・調整する。

| # | 項目 | 確認内容 |
|---|------|----------|
| 1 | 保存先 | `.docs/adr/` が当該プロジェクトのドキュメント配置と整合するか確認したか。異なる場合は Phase 5 のパスを実配置へ合わせたか |
| 2 | 証跡として使える記録 | そのプロジェクトで実際に使えるもの（PR・Issue・チャット・タスク管理ツール）を特定し、「証跡」節の例示を実態へ合わせたか |
| 3 | 対象範囲 | 業務判断まで ADR にするか、技術判断に限るかを決めたか。限る場合は「概要」の対象記述を調整したか |
| 4 | 承認の運用 | 通常の技術判断を PR レビューで承認とするか、別の承認経路があるかを確定したか |
| 5 | 連携先スキルのリンク | 「関連スキル」節が**リンクしている** 4スキル（system-design / spec-planning / knowledge-base-management / documentation-management）のうち配布先に無いものを、行ごと削ったか。`ticket-creation` は description 内で名前を挙げるだけでリンクしていないため、この確認の対象外 |
| 6 | 契約チェッカー | `scripts/check-adr.py` を配備したか。配備しない場合、契約が守られているかを何で確認するか（PRレビュー等）を決めたか |
| 7 | 既存 ADR の status 移行 | 配布先に既に `.docs/adr/` がある場合、旧版や他運用の status 語彙が残っていないか確認し、[reference.md](./reference.md) セクション7 の対応表で読み替えたか |

## 失敗の記録と反映

このスキルの実行で失敗・見落とし・誤りが起きたら、**その場で下表に追記する**。
表に行を足すだけで本文を直さないのは記録ではなく放置。必ず本文へ反映する。
規約: [skill-self-improvement.md](../../docs/skill-self-improvement.md)

### 記録する条件

- 確定済み ADR の本文を書き換えてしまった
- 検討中・置換・失効のレコードを実装根拠にしてしまった
- 出典が後から辿れず、判断の根拠を再確認できなかった
- 複数の論点を1レコードに束ね、一部の変更で全体を置換する羽目になった

### 反映の手順

1. 上表に1行追加する
2. **本文の該当箇所を直す**（チェックリスト項目の追加、手順の明確化など）
3. 機械的に検出できる失敗なら `scripts/` の検証へ追加し、回帰テストを書く
4. Version History にバージョンを上げて記録する
