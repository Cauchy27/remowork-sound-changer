## 1. ADR テンプレート

`.docs/adr/YYYYMMDD-{short-title}.md` に保存する。1ファイル1論点。

```markdown
---
status: 検討中
決定日: YYYY-MM-DD
決定者: {担当者・チーム}
出典:
  - {URL または一意のID}（{何の記録か} / {承認内容の1行要約}）
置換先:
---

# {判断を1文で。人が3秒で分かる書き方にする}

## 背景

{なぜこの判断が必要になったか。前提となる制約}

## 決定内容

{何を採用するか。1論点だけを書く}

## 検討した代替案

- {案B}: {棄却理由}
- {案C}: {棄却理由}
- 現状維持: {棄却理由}

## 影響・代償

- ポジティブ: {期待される効果}
- ネガティブ: {生じるデメリット・コスト}
- 移行コスト: {概算工数・手順概要}

## 再検討条件

{この判断が覆る条件。前提が変わったら再判断する、という形で書く}

## 関連する決定

{関連する ADR の ID。無ければ「なし」}
```

### frontmatter の規則

| キー | 必須 | 備考 |
|---|---|---|
| `status` | 常に | 検討中 / 確定 / 置換 / 失効 のいずれか |
| `決定日` | 常に | `YYYY-MM-DD` |
| `決定者` | 常に | 個人名またはチーム名 |
| `出典` | 常に（1件以上） | **確定にするときは第三者が後から参照できる記録に限る。** AI会話のみは不可。**URL または一意のID を含めること。**「タスク『〇〇』のコメント」のような文字列だけでは、後から同じ記録に辿り着けない。リンクは消えうるため、**承認内容の1行要約を併記する** |
| `置換先` | 置換のときのみ | 置換先 ADR のファイル名（stem） |

status を「失効」にするときは、本文末尾に `## 失効理由` を設け、`- YYYY-MM-DD: 理由` の形で追記する。

## 2. 記入例（架空案件）

実在の案件・人物・機密情報を記入例に転記しないこと。以下は架空の社内在庫管理システム。

### 例A: 技術選定（選択肢比較あり）

```markdown
---
status: 確定
決定日: 2026-08-20
決定者: 開発チーム
出典:
  - https://github.com/example-org/example-repo/pull/142#discussion_r1234567890 （PR #142 のレビューコメント。採用合意）
置換先:
---

# 在庫の履歴保持にイベントソーシングを採用せず、更新日時つきスナップショット方式にする

## 背景

在庫数の変更履歴を追跡したい要求が出た。現行はスナップショットのみで履歴を持たない。

## 決定内容

在庫テーブルに更新履歴テーブルを併設し、変更のたびに1行追記する方式にする。

## 検討した代替案

- イベントソーシング: 履歴の表現力は高いが、現在庫の参照が集計になり、既存の一覧画面の応答が悪化する。チームに運用経験がない
- 監査ログのみ: 参照系から使えず、画面要求を満たせない
- 現状維持: 履歴要求を満たせない

## 影響・代償

- ポジティブ: 既存の参照系を変えずに履歴を持てる
- ネガティブ: 書き込みが2テーブルになり、トランザクション境界の管理が要る
- 移行コスト: 履歴テーブル追加とマイグレーションで3人日程度

## 再検討条件

履歴の参照要件が「任意時点の在庫の再構築」まで広がった場合は再判断する。

## 関連する決定

なし
```

### 例B: 業務判断（選択肢比較なし・捨てた案のみ）

```markdown
---
status: 確定
決定日: 2026-08-20
決定者: 松川
出典:
  - https://example.com/tasks/12345#comment-67890 （タスク「在庫調整の運用ルール」での承認返信。2026-08-20）
置換先:
---

# 棚卸し差異の調整は、店舗側では確定せず本部承認を必須にする

## 背景

店舗が自由に在庫を書き換えられると、差異の原因追跡ができなくなる。

## 決定内容

店舗からの在庫調整は申請として登録し、本部の承認をもって在庫へ反映する。

## 検討した代替案

- 店舗即時確定＋事後監査: 差異の原因が特定できた実績が乏しく、監査が形骸化する見込み

## 影響・代償

- ポジティブ: 差異の原因を承認時点で記録できる
- ネガティブ: 反映までに時間差が生じ、当日の在庫が実態とずれる
- 移行コスト: 申請・承認画面の追加が必要

## 再検討条件

本部の承認が滞留して業務が止まる場合は、金額しきい値による自動承認を再検討する。

## 関連する決定

なし
```

## 3. 選択肢比較マトリクスの書式と評価軸

技術選定・アーキテクチャ決定で使う。評価軸は3〜5項目に絞る。多いと比較が薄くなる。

```markdown
| 選択肢 | 開発コスト | 運用コスト | チーム習熟度 | 長期サポート | 総合 |
|--------|-----------|-----------|------------|------------|------|
| 案A | 中 | 低 | 高 | 良好 | **採用** |
| 案B | 低 | 高 | 低 | 不透明 | 却下 |
| 現状維持 | なし | 中 | 高 | - | 却下 |
```

### 評価軸の候補

- 開発コスト・運用コスト
- スケーラビリティ・パフォーマンス
- セキュリティ・コンプライアンス
- チームのスキル習熟度
- エコシステム・長期サポート
- 後戻りのしやすさ（判断を覆すときのコスト）

**「後戻りのしやすさ」は特に有効。** 覆しやすい判断は速く決めてよく、覆しにくい判断だけ時間をかければよい。

## 4. サブエージェント活用の起動手順

影響範囲が大きい技術選定でのみ使う。**3視点を1つのレスポンス内で同時起動する（逐次実行禁止）。**

| subagent_type | 役割 | 定義 |
| --- | --- | --- |
| `solution-architect` | システム全体設計・非機能要件（スケーラビリティ/可用性）の観点で評価 | `.claude/agents/development/solution-architect.md` |
| `cto` | 技術戦略・長期的な技術負債リスクの観点で評価 | `.claude/agents/executive/cto.md` |
| `tech-lead` | 実装難易度・チームの習熟度・保守性の観点で評価 | `.claude/agents/development/tech-lead.md` |

```markdown
Task(
  subagent_type="solution-architect",
  description="ADR選択肢のアーキテクチャ観点レビュー",
  prompt="
    検討中のADR: {タイトル・背景}
    選択肢: {Phase 2 で列挙した選択肢一覧}
    システム全体設計・非機能要件（スケーラビリティ/可用性）の観点で各選択肢を評価すること。
    出力先: .tmp/architecture/solution-architect-review.md に書き出し、本文への返答は3-5行の要約のみとすること。
  "
)

Task(
  subagent_type="cto",
  description="ADR選択肢の技術戦略レビュー",
  prompt="
    検討中のADR: {タイトル・背景}
    選択肢: {Phase 2 で列挙した選択肢一覧}
    技術戦略・長期的な技術負債リスクの観点で各選択肢を評価すること。
    出力先: .tmp/architecture/cto-review.md に書き出し、本文への返答は3-5行の要約のみとすること。
  "
)

Task(
  subagent_type="tech-lead",
  description="ADR選択肢の実装観点レビュー",
  prompt="
    検討中のADR: {タイトル・背景}
    選択肢: {Phase 2 で列挙した選択肢一覧}
    実装難易度・チームの習熟度・保守性の観点で各選択肢を評価すること。
    出力先: .tmp/architecture/tech-lead-review.md に書き出し、本文への返答は3-5行の要約のみとすること。
  "
)
```

3視点の結果を Phase 2 の比較マトリクスへ統合し、Phase 3 の意思決定の根拠にする。

## 5. 既存の散在した判断を移行する（オプション）

既に口頭・チャット・タスクコメントに判断が散在しているプロジェクトへ ADR を導入する場合の、1回限りの手順。通常のワークフローには含めない。

1. 散在している判断を洗い出し、**すべて `status: 検討中`** で取り込む。この時点では実装根拠にしない
2. 1件ずつ出典を辿り、決定者・決定内容・決定日を再確認する
3. 現在も採用している判断は、出典を追跡可能な記録に差し替えたうえで「確定」へ上げる
4. 誤り・旧判断と判明したものは、**一度「確定」にせず**「置換」または「失効」へ直接送る。存在しなかった決定を歴史として作らないため
5. 設計書・モック・実装と矛盾するものは、その場で決めずユーザーへ確認し、裁定後に確定させる

移行が終わるまでは「検討中」が多数残る。件数がゼロになること自体は導入完了の条件ではない。**出典が追跡可能な形で埋まり、矛盾が解消されていること**が条件である。

移行対象が多く、認識差の裁定に時間がかかる場合は、未裁定の争点を `.docs/adr/discrepancies/` に分離して決定レコードと混ぜないという運用も選べる。件数が少ないうちは分離せず、確認事項としてユーザーへ提示すれば足りる。

## 6. Troubleshooting

### 選択肢が多すぎてまとまらない

原因: 問題スコープが広すぎる、または評価軸が不統一。

1. 「この決定で何を変えるのか」を1文で定義する
2. 評価軸を3〜5項目に絞る
3. 明らかに非現実的な案は最初に除外する

### 過去の ADR と整合が取れない

原因: 関連 ADR の見落とし、または前提条件の変化。

1. `Grep` で `.docs/adr/` を検索し、関連するものを洗い出す
2. 旧 ADR の status を「置換」にし、`置換先` に新 ADR の ID を書く
3. 前提条件の変化を新 ADR の「背景」に明記する

**旧 ADR の本文は書き換えない。** 置換関係で履歴を表現する。

### 確定済み ADR の記述が間違っていた

本文を直さない。正しい内容の後続 ADR を作り、旧レコードを「置換」にする。誤りがあった事実も記録の一部として残す。

誤字脱字など判断内容に影響しない修正だけは、本文を直してよい。判断・理由・代償に関わる箇所は対象外。

### 1つの ADR に論点が増えてしまった

分割する。1レコード1論点を守れないと、1項目の変更でレコード全体を置換することになり、履歴が読めなくなる。

分割の目安: 「この1件だけを後から覆せるか」で切る。覆せないなら分ける。

## 7. 既存 ADR の status 移行
本スキルの旧版や他の運用で作られた ADR がある場合は、下表で読み替える。**既存レコードの本文は書き換えず、frontmatter の `status` だけを対応する語へ置き換える。**

| 既存の表記 | 本スキルの status | 備考 |
|---|---|---|
| 提案中 / proposed | 検討中 | 実装根拠にしない |
| 承認済 / accepted | 確定 | 出典が追跡可能か確認する。不足なら検討中へ戻す |
| 置換済 / superseded | 置換 | `置換先` に後続 ADR の ID を入れる |
| 廃止 / retired / deprecated | 失効 | `## 失効理由` を追記する |
| 確認中 | 検討中 | 出典の再照合が終わっていない状態を指す場合が多い |
| status なし | 検討中 | 承認の有無が不明なため、根拠にする前に確認する |

**「承認済」を機械的に「確定」へ移さない。** 出典が後から辿れないレコードは、確定にせず検討中に置いて出典を補ってから上げる。移行を機に、根拠のない判断が確定として通ってしまうのを防ぐため。

### 本スキル v1.1.0 以前のフォーマットからの変換

v1.1.0 のテンプレートは、メタデータを frontmatter ではなく**本文の箇条書き**に置いていた。この形式のレコードは Phase 0 の `status` 判定（frontmatter を見る）に引っかからず、**存在しないものとして扱われてしまう**。放置すると確定済みの判断が見落とされる。

旧形式の例:

```markdown
# ADR-001: {タイトル}

- **日付:** 2026-08-02
- **ステータス:** 承認済
- **決定者:** 開発チーム
```

変換手順:

1. `python3 scripts/check-adr.py .docs/adr` を実行する。旧形式は「status が frontmatter になく、本文に「承認済」が埋め込まれている」と報告される
2. 本文の `- **日付:**` `- **ステータス:**` `- **決定者:**` を frontmatter の `決定日` / `status` / `決定者` へ移す。status は上の対応表で読み替える
3. **出典は旧形式に存在しない。** 補えないレコードは `確定` にせず `検討中` へ置く。出典が辿れないものを確定として引き継がない
4. 既存の frontmatter（`type` / `tags` / `timestamp` などプロジェクト独自のキー）は消さずに残す。本スキルは追加するキーだけを規定し、既存キーの削除は求めない
5. 本文の見出し構成が異なっていても書き換えない。**旧レコードの本文は判断の記録そのもの**であり、整形のために改変しない
6. `index.md` / `README.md` に status 列がある場合は、同じ対応表で読み替える

変換は1回限りの作業である。**変換しないという選択もある。** その場合は、旧形式のレコードが Phase 0 の検索に引っかからないことを承知したうえで、`.docs/adr/README.md` に「YYYY-MM-DD 以前のレコードは旧形式。参照時は本文のステータスを見ること」と明記する。
