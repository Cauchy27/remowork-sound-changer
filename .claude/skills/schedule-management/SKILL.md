# スケジュール管理スキル

## 使用宣言（必須）

```
[schedule-management スキルを使用します]
```

## 概要

`.claude/schedule.md` を「期限とマイルストーン」の単一ソースとして維持する。
マイルストーン・週次タスク・期限を一元管理し、セッション終了時に自動更新。

進捗トラッキング3層モデルにおける **L2（時間層）** を担当する。層構造・同期方向の正本は
`.claude/docs/progress-tracking-model.md`。L1（戦略層・roadmap.md の中身の組み替え）は
roadmap-planning、L3（実行層・チケット単位の進行管理）は ticket-creation の担当であり、
本スキルの範囲外。

**書き込みの専権**: `.claude/schedule.md` を編集するのは本スキルのみ。roadmap-planning /
sprint-planning / ticket-creation は完了・遅延・ブロック等の状態を本スキルへ引き渡す・報告する
だけであり、`.claude/schedule.md` を直接編集しない。他スキル側から見た手順は各スキルの
SKILL.md（`../roadmap-planning/SKILL.md` 等）を参照。

## 発動条件

- 「スケジュール確認」「期限いつ？」「いつまでに」「マイルストーン」
- session-briefing から自動呼び出し（オーケストレーション）
- 明示的に呼び出し

---

## 対象範囲

schedule.md が持つのは以下の2種類のみ。

- **マイルストーン**: 日付が確定した節目
- **週次タスク**: その週限りの雑務

個別チケットのタスク名を schedule.md に列挙しない（L3 との複製禁止）。チケット単位の実装内容は
ticket-creation / spec-planning / sprint-planning が管理する側を参照する。

---

## 初期セットアップ

`.claude/schedule.md` が存在しない場合、黙って進めず「schedule.md が未整備です」と報告したうえで、
下記テンプレートから新規生成する。

1. `.claude/schedule.md` の有無を確認する
2. 存在しない場合: 「未整備」と報告 → 下記「schedule.md の構造」のテンプレートで新規作成 →
   `.claude/roadmap.md` があれば「roadmap.md からの受け取り」節の手順で初期マイルストーンを取り込む
3. 存在する場合: そのまま通常操作へ進む

## schedule.md の構造

```markdown
# プロジェクトスケジュール

最終更新: YYYY-MM-DD

## マイルストーン

| # | マイルストーン | 期限 | 状態 | 対応テーマ（roadmap.md） | 実行チケット | 備考 |
|---|-------------|------|------|------------------------|------------|------|
| 1 | Phase 1: {概要} | YYYY-MM-DD | 完了 | {L1 テーマ名} | {件数 or リンクのみ} | {備考} |
| 2 | Phase 2: {概要} | YYYY-MM-DD | 未着手 | {L1 テーマ名} | {件数 or リンクのみ} | {備考} |

## 今週のタスク

| 優先度 | タスク | 期限 | 状態 | 備考 |
|--------|--------|------|------|------|
| 高 | {タスク} | YYYY-MM-DD | 未着手/進行中/完了 | {メモ} |

## 確認事項・メモ

- {思いついたこと}
- {確認したいこと}
```

「実行チケット」列にはタスク名を書かない。件数、または taskhub / `.docs/ticket/` へのリンクのみとする。

マイルストーン表の「状態」列が取りうる値は「未着手 / 進行中 / 完了 / 遅延 / ブロック」の5種。
「遅延」「ブロック」を設定した場合は、必ず「備考」列に理由を1行で書く（例:
「備考: 外部API仕様確定待ちで2週間遅延」）。

## roadmap.md からの受け取り（L1 → L2）

roadmap-planning の Phase 6 が `.claude/roadmap.md` の四半期テーマから日付確定済みの節目を渡してくる。
受け取った側（本スキル）の手順:

1. 渡された節目を「マイルストーン」表へ1行として追加する
2. 「対応テーマ（roadmap.md）」列に該当テーマ名を記入し、L1 との対応づけを残す
3. タスクの詳細（実装内容）は書き写さない。詳細が必要な場合は L1 側を参照する

roadmap.md 側の記述を書き換える必要が生じた場合は roadmap-planning に差し戻す（本スキルは
roadmap.md を編集しない）。

## 操作

### タスク追加

```
「XXXをスケジュールに追加して」
→ schedule.md の該当セクションに追記
```

### タスク完了

```
「XXXを完了にして」
→ 状態を「完了」に更新
```

### 期限確認

```
「次の期限は？」
→ 未完了タスクを期限順でリスト表示
```

### 週次レビュー

```
「今週のタスクを整理して」
→ 完了タスクをアーカイブ、来週分を追加
```

## 状態ロールアップ（L3 → L2 → L1）

L3（ticket-creation）から受け取る状態は **完了 / 遅延 / ブロック** の3種。完了だけでなく、
下層で期限に間に合わないと判明した時点で（完了を待たずに）マイルストーンの状態を更新する。

1. L3 → L2: ticket-creation からチケットの状態変化（完了 / 遅延 / ブロック）の報告を受けたら、
   当該チケットが紐づくマイルストーンの状態を次の基準で更新する。
   - **遅延・ブロック**: 報告を受けた時点で即座にマイルストーンの状態を「遅延」または
     「ブロック」に更新し、「備考」列に理由を1行で書く
   - **完了**: 下記「完了判定の手順」に従い、該当マイルストーン配下の全チケットが完了して
     いることを確認したうえで、マイルストーンの状態を「完了」に更新する
2. L2 → L1: 「対応テーマ（roadmap.md）」に紐づくマイルストーンが全て「完了」になったら、
   roadmap-planning に完了を伝え、`.claude/roadmap.md` 側の該当テーマへ完了印を付けてもらう
3. いずれの段階でも、上層へ渡すのは状態（完了 / 遅延 / ブロック）のみ。タスク名や実装詳細は
   複製しない

### 完了判定の手順

マイルストーンを「完了」にする前に、以下の手順で機械的に確認する。

1. マイルストーン表の「実行チケット」列と、チケット側の「マイルストーン（L2）」欄を対応
   キーとする
2. 該当マイルストーン名で `grep` し、紐づくチケット群を列挙する（例:
   `grep -rl "マイルストーン（L2）.*{マイルストーン名}" ../taskhub/teams/{TEAM_NAME}/{REPO_NAME}/tickets/ .docs/ticket/ 2>/dev/null`）
3. 列挙した全チケットの「状態」フィールドが「完了」であることを確認する
4. 1件でも「完了」以外が残っている場合はマイルストーンを完了にせず、未完了チケットを
   「実行チケット」列または備考に残す

## 自動処理

| タイミング | 処理 |
|-----------|------|
| セッション開始時 | schedule.md を読み取り、期限切れ・期限間近を警告 |
| セッション終了時 | 完了タスクの状態更新、コミット＆プッシュ（ユーザー指示時） |
| タスク完了時 | 即座に schedule.md を更新 |
| ticket-creation からチケット状態（完了/遅延/ブロック）の報告を受けたとき | 「状態ロールアップ」の手順で当該マイルストーンの状態を更新（遅延・ブロックは即時、完了は完了判定の手順を経て反映） |

マイルストーン単位のロールアップのうちマイルストーン表全体の棚卸し（複数マイルストーンの
一括確認）は自動処理の対象外とし、「マイルストーンを整理して」等の明示指示で手動実行する。
