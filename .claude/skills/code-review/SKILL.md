# 統合コードレビュースキル

## 🔴 使用宣言（必須）

このスキルを使用する際は、必ず最初に以下を出力すること：

```
[code-review スキルを使用します]
```

## 概要

このスキルは**コード実装**を対象にレビューを実行する。視点（誰が見るか）・観点（何を見るか）・裁定ルール・実行経路の優先順位・総合判定の共通定義は [`.claude/docs/review-matrix.md`](../../docs/review-matrix.md)（全レビュースキル共通の正本）にあり、**本スキルでは再掲しない**。

| 項目 | 本スキルでの値 |
|------|--------------|
| 対象 | コード実装 |
| 使う視点（第1層・誰が見るか） | Claude Code / Codex / Antigravity（3視点・実CLI優先） |
| 使う観点（第2層・何を見るか） | 1 要件充足 / 2 アーキテクチャ・構造 / 3 実装品質・エッジケース / 4 セキュリティ / 7 運用・保守（+ 課金・料金が絡むなら 6 経営・事業 / 外部規約が絡むなら 9 規約・コンプライアンス） |
| 第3層チェックリスト | 本スキル固有の**コード実装チェックリスト（13項目）**。[`agents/code-checklist-13.md`](./agents/code-checklist-13.md) |
| 横断ゲート | 本質ギャルレビュー（視点・観点のカウントに含めない独立枠。後述） |

### 用語の是正（必読）

**旧称「13視点」は誤用だった。** 13項目は「観点をどう見るか」の第3層チェックリストであり、正本でいう「視点（誰が見るか）」ではない。本スキルでは以後「コード実装チェックリスト（13項目）」または「13項目チェックリスト」と呼ぶ。この用語衝突が `internal-structure-review`（3視点）との統合を妨げていたため是正した。ファイルも `agents/13-perspectives-unified.md` から `agents/code-checklist-13.md` へ改名している。

## 🔴 レビュー対象の単位（実装中に呼ばれた場合）

実装作業の途中で本スキルが呼ばれた場合、**レビュー対象は「1ページ / 1機能」単位**とする。
ファイル追加・関数追加・小修正のたびに本スキルを起動しない。実装単位が**動作する状態**に達した時点で1回だけ起動する。
P0/P1 の修正後は、**再確認を修正差分に限定**し、本スキルのフルラウンドを再実行しない。

| 種別 | 1単位に含めるもの |
|------|-----------------|
| 画面（ページ） | 画面 + API 接続 + その画面の対象テスト |
| 機能（画面をまたぐ） | 機能に属する全画面・全エンドポイント + 対象テスト |
| API 単体（画面なし） | 関連エンドポイント群 + スキーマ/型 + 対象テスト |
| バグ修正 | 該当バグの修正 + 回帰テスト |

> PR レビュー・リリース前レビューなど、**レビュー自体が目的で呼ばれた場合は本節の対象外**（対象範囲はユーザー指定に従う）。

## 🔴 横断ゲート: 本質ギャルレビュー（必須・全視点共通・Round 1 先頭）

**3層構造（視点・観点・チェックリスト）に入る前の、前提・目的・意思決定を検証する事前フィルタである。** 3視点レビューへ分岐する前に、[essence-gyaru-review](../essence-gyaru-review/SKILL.md) を必ず1回実行すること。skip不可。

- Claude Code / Codex / Antigravity の3視点の**カウントに含めない独立枠**。目的・意思決定・前提・因果・矛盾・業務上の代償・次アクションの7軸で対象を突く
- `review-iteration` は本レビューの周回番号（初回1、再レビューごとに加算）と揃える
- **`code-review` を単体で再実行する場合の `review-iteration` 決定手順**: 同一対象への前回レビューがあれば「前回 `review-iteration` + 1」を使う。前回値は `.tmp/ai-review/gyaru/round-*/report.md` の最大番号等から確認する。前回が存在しない初回は 1 とする
- 出力先: `.tmp/ai-review/gyaru/round-{review-iteration}/report.md`
- essence-gyaru-review の Instructions（Task で `essence-gyaru-reviewer` を起動 → `validate_report.py` で構造検証）に従う
- 全指摘ID（`GYARU-{review-iteration}-{3桁}`）と件数を控え、Round 2（裁定）・Round 3（統合）・Round 4（fact-check）へそのまま引き渡す

## 🔴 3視点の起動方法（Tier 1〜3・必須試行・Round 1）

**Tier 1 はレビュー対象の内容を Codex（OpenAI）/ Antigravity（Google）へ外部送信する。** 認証情報・個人情報・非公開の契約コード・顧客データを含む対象では Tier 1 を使わず Tier 3（Claude Code 内の別視点）に限定すること。判断基準は正本（[review-matrix.md](../../docs/review-matrix.md)「外部送信に関する注意」）に従う。

**3視点（Claude Code / Codex / Antigravity）は全て必須試行。省略・条件付き実行は禁止。**
実行経路の優先順位（Tier 1〜3）・独立性の申告フォーマットは正本（[review-matrix.md](../../docs/review-matrix.md)）の定義に従う。**ここでは再掲しない。**

視点ごとに Tier 判定は独立に行う。**1視点が Tier 3 に落ちても、他の視点まで道連れにしない。**

**重い一括レビューを CLI/MCP へ1発で投げると、成果物ゼロのままタイムアウトする。** 必ず観点単位・ファイル単位に分割すること。エラー対処・既知の失敗パターンの詳細は [`ai-cli-execution` スキル](../ai-cli-execution/SKILL.md)（[reference.md](../ai-cli-execution/reference.md) §5・§6 が正本）に従う。**本スキルでは再掲しない。**

共通プロンプト雛形（4要素）・Claude Code/Codex/Antigravity 各視点の Step 0（疎通確認）/Step 1（レビュー実行）の実行コマンド全文・Tier 3（Task tool + ペルソナ）フォールバックのコード例は [reference.md](./reference.md) セクション1を参照。

## Round構成

```
Round 1: 横断ゲート（本質ギャルレビュー・必須）+ 3視点独立レビュー（Claude Code / Codex / Antigravity）
Round 2: 不一致の抽出と裁定  ← 新設。正本の裁定ルールに従う
Round 3: 結果統合
Round 4: ファクトチェック（code-review-fact-check スキル・必須）
```

### Round 1: 3視点独立レビュー

観点 1・2・7 は合議観点であり、3視点が重複して見る（正本参照）。**合議観点は全視点が確認する前提で、各視点はその中でも強みを活かして重点的に見る。** 残りの観点（3・4・該当時6・9）は各視点の強みに応じて主担当を割り振る。

**下表は正本の「主担当の観点」（対象横断の一般定義）そのものではなく、コード実装レビューに限定した重点配分である。** 正本ではデザイン・ドキュメント全般が主担当の Antigravity も、コード実装では観点5・8の出番が乏しいため、代わりに合議観点のうち構造・運用保守を重点的に見る配分にしている。

| 視点 | 各視点の重点担当観点（コード実装向け） |
|------|------------------------------------------|
| Claude Code | 2 アーキテクチャ・構造 / 4 セキュリティ / 6 経営・事業（該当時。課金導線・料金体系変更等では `ceo-reviewer`/`cmo-advisor` を追加起動。詳細は前節「第3層」参照） |
| Codex | 1 要件充足 / 3 実装品質・エッジケース / 9 規約・コンプライアンス（該当時） |
| Antigravity | 2 アーキテクチャ・構造 / 7 運用・保守（コード実装では UX・ドキュメントの出番は限定的だが、UI コンポーネントを含む変更では観点5相当の指摘も追加で拾う） |

各視点は `agents/code-checklist-13.md` の該当項目を用いて判定する。Business Logic 項目は同ファイルの sonnet-uplift 品質ゲートに従う（「要親判断」の扱いは変更しない）。

### Round 2: 不一致の抽出と裁定（新設）

**Round 2 の着手前に、稼働している視点数を確認する。** Round 1 で3視点それぞれの `EXIT`・出力ファイルの非空・OAuth失効/利用制限の有無を確認し、Tier 3 へ落ちた視点や出力空の視点を数え、稼働視点数（0〜3）を確定する。**稼働視点が1つ以下の場合、Round 2（不一致の抽出と裁定）は成立しない。** その場合の扱い（Round 1 単独結果のみ記録・Round 2「実施不可」明記・総合判定「保留」または「暫定」）は正本（[review-matrix.md](../../docs/review-matrix.md)）の「視点が縮退した場合の扱い」節にそのまま従う。

稼働視点が2以上の場合のみ、以下の裁定手順に進む。**手順は正本の「裁定ルール」に従う。ここでは再掲しない。** 要点のみ:

1. 3視点で判定が割れた項目を抽出する（合議観点で特に発生しやすい）
2. 各視点が「何を前提に」その判定をしたかを読む
3. 一次情報（実ファイル・実コマンドの実行・公式ドキュメント）で決着させる
4. **多数決で潰さない。** 決着しない場合は正本のエスカレーション基準に従い管理者へ

裁定結果は正本の出力フォーマット（「判定が割れた項目（裁定結果）」テーブル）に従って記録し、Round 3 の統合へ引き渡す。裁定者はオーケストレーター（トップレベルの Claude Code セッション）。

### Round 3: 結果統合

Round 1 の一致した指摘、Round 2 の裁定結果、横断ゲートで得た本質ギャルレビューの全指摘IDを合わせて、下記「統合レビュー結果テンプレート」で統合結果を出力する。ギャル指摘は3視点/13項目のカウントに含めず、統合レビュー結果に別枠として記載する。

### Round 4: ファクトチェック（必須）

結果統合（Round 3）が完了したら、統合レビュー結果をそのまま最終成果物にせず、必ず `code-review-fact-check スキル` を Round 4 として実行し、実コード照合で「妥当/部分的に妥当/過剰/事実誤認」を判定すること。GYARU-* を含む全指摘が検証対象。

ファクトチェックで「妥当」と判定された指摘のみを最終 PR コメント・レビュー結果に採用する。詳細な実行手順（4 Phase・4択判定区分・出力テンプレート）は `code-review-fact-check/SKILL.md` を参照。

## レビューの姿勢（絶対ルール）

**レビューは時間がかかっても構わない。網羅性が最も大事。**

| 原則 | 説明 |
|------|------|
| **時間をかけてよい** | レビューに時間がかかることは問題ではない。急いで見落とすほうが問題 |
| **網羅性が最優先** | 軽微な問題も含めて全て洗い出す。「些細だから」で見逃さない |
| **全ファイルを確認** | 変更があったファイルだけでなく、影響範囲のファイルも確認する |
| **3視点とも必ず試行** | Claude Code / Codex / Antigravity は全て必須試行。コード実装レビューで Antigravity だけ条件付きにはしない。実行経路の優先順位は正本（[review-matrix.md](../../docs/review-matrix.md)「実行経路の優先順位」）に従う |

## 批判的レビューの原則（必須）

**レビューは批判的に行うこと。**

| 原則                       | 説明                                               |
| -------------------------- | -------------------------------------------------- |
| **問題を探す姿勢**         | 「問題がない」ではなく「問題を見つける」姿勢で臨む |
| **仮定を疑う**             | 実装者の仮定・前提条件が正しいか検証する           |
| **エッジケースを想定**     | 正常系だけでなく異常系・境界値を重点的に確認       |
| **セキュリティ最優先**     | 脆弱性がないか徹底的に調査する                     |
| **ビジネスロジックの正しさ** | 金額計算、状態遷移、外部データ変換が仕様通りか検証 |

**禁止事項:**

- 「問題ありません」で終わらせない
- 表面的な確認で済ませない
- 実装者の意図を無条件に信用しない

## レビューコメントの優先度

**本スキルにおける優先度記法の定義はこの表のみ。** 他ファイル（`agents/codex-reviewer.md` 等）は本表の記法を使用するだけで再定義しない。正本（[review-matrix.md](../../docs/review-matrix.md)「優先度の共通記法」節）に全レビュースキル共通の尺度（Critical/Major/Minor/Question/Positive）が定義済みであり、下表はその共通尺度への本スキルでの対応表記である。

| 優先度   | 記法       | 説明                             | 正本の共通尺度 |
| -------- | ---------- | -------------------------------- | -------------- |
| 必須対応 | `[MUST]`   | マージ前に必ず修正が必要         | Critical |
| 推奨     | `[SHOULD]` | 修正が望ましいが、理由があればOK | Major |
| 提案     | `[NIT]`    | 細かい指摘、対応は任意           | Minor |
| 質問     | `[Q]`      | 意図の確認、理解のための質問     | Question |
| 称賛     | `[GOOD]`   | 良い実装へのコメント             | Positive |
