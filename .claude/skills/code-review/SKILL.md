# 統合コードレビュースキル

## 🔴 使用宣言（必須）

このスキルを使用する際は、必ず最初に以下を出力すること：

```
[code-review スキルを使用します]
```

## 概要

ドキュメント・コードを **2系統で並列レビュー** するスキル。

- **Claude Code**: モードA（Codex 利用可能時）は 13視点エージェント、モードB（Codex 不可時）は Task tool で4視点並列
- **Codex**: 独立レビュー。経路は **CLI（`codex exec`）が既定**、MCP はフォールバック
- **Antigravity**（`agy` 利用可能時）: デザイン・UX・情報設計の観点を担当

## 📖 技術情報の参照

**技術的な情報（ライブラリのAPI、フレームワークの仕様、ベストプラクティス等）を調べる際は、必ず Context7 MCP を使用すること。**

```
手順:
1. resolve-library-id でライブラリIDを解決
2. query-docs でドキュメントを取得
```

## 🗜️ コンテキスト節約

**作業中のコンテキスト肥大化を防ぐため、以下を遵守すること。**

- **サブエージェントを積極活用**: 調査・実装・テストはサブエージェントに委託し、メインコンテキストを圧迫しない
- **結果はファイルに書き出す**: `.tmp/{task_name}/` に出力し、メインへの返答は 3-5 行の要約のみ
- **大きなファイルは部分読み**: offset/limit を活用し、全文読み込みを避ける
- **リファレンスは遅延読み込み**: 必要なステップでのみ読み込み、最初に全て読まない

## 🔴 Codex レビューは必須試行（絶対ルール）

**レビュー実行時、Codex による独立レビューを必ず試行すること。**
**スキップは禁止。利用不可の場合のみフォールバックを許可する。**

### 実行経路の優先順位（CLI > MCP > Claude 別視点）

| Tier | 手段 | 使う条件 |
|------|------|----------|
| **1** | **Codex CLI**（`codex exec` / `codex exec review`） | **既定**。PATH にあり認証済みなら必ずこちら |
| 2 | Codex MCP（`mcp__codex__codex` / `codex-reply`） | CLI が使えない場合のみ。**タスク分割必須** |
| 3 | Claude Code 組み込みエージェント | Codex 自体が使えない場合の代替 |

詳細は [`.claude/docs/ai-cli-execution-policy.md`](../../docs/ai-cli-execution-policy.md) を参照。

### 実行前の確認（Step 0）

```bash
command -v codex && codex --version
```

1. **出力あり** → Tier 1（CLI）でレビューを実行
2. **出力なし** → **セットアップ手順を案内**（下記）してから Tier 2（MCP）を確認
3. MCP も使えない → 次項の報告を出し、**作業を止めずに Tier 3 で継続**する

**判断を仰いで停止しない。** 案内と注記を出したうえで下位 Tier に落として続行する。

### CLI が未設定の場合の案内（必須・省略禁止）

````markdown
Codex CLI が未設定のため、レビューの第1経路が使えません。

【現状】
- `command -v codex`: {結果}

【セットアップ手順】

```bash
npm install -g @openai/codex
```

```bash
codex login
```

インストール後、`codex --version` でバージョンが出れば設定完了です。

【このまま進める場合】
Codex MCP（Tier 2）へフォールバックします。MCP はタイムアウトのためタスク分割が必要で、
CLI より所要時間が伸びます。
````

### 利用不可の場合の報告（CLI・MCP とも不可）

**作業を止めない。** 次を報告したうえで Tier 3 に落として継続する。

```
Codex が利用できません（CLI 未設定 / MCP 未接続）。
Tier 3（Claude Code の別視点）で継続します。同一モデル系による自己レビューのため、独立性は低下します。

先に Codex CLI を設定して再実行したい場合は、上記セットアップ手順の実施後にレビューを再依頼してください。
```

### 禁止事項

- Codex が利用可能なのにスキップすること
- **CLI が使えるのに MCP を選ぶこと**
- **CLI 未設定を検出しながら、セットアップ手順を案内せず黙ってフォールバックすること**
- **MCP 経路でタスク分割せずに重いレビューを1発で投げること**（必ずタイムアウトする）
- **`codex exec review` に対象指定と観点プロンプトを併用すること**（`exit 2` になる）
- **`review` サブコマンドで `-s read-only` を省略すること**（review も設定済み sandbox を継承するため、書き込み可能環境ではワークツリーを変更されうる）
- **出力先ディレクトリを作らずに `-o` を指定すること**（書き込みに失敗し結果を失う）
- **ゴールを明示しないプロンプトを投げること**（プロンプト設計ルールは後述）
- Codex の結果を統合レビューに含めないこと
- Tier を下げた事実を成果物に書かないこと

## 🔴 Codex 実行

### 🔴 プロンプト設計ルール（経路共通・必須）

**Codex へ投入する全プロンプトは、必ず冒頭に「ゴールは〜」で始まる1文を置き、達成すべき成果を明示すること。**
あわせて4要素（ゴール / コンテキスト / 制約 / 完了条件）で構成する。

- テンプレート・注意点の詳細: [`.claude/docs/codex-prompt-guideline.md`](../../docs/codex-prompt-guideline.md) を参照
- レビュー依頼・実装依頼・調査依頼など、Codex に指示を出す全ての場面に適用

### Tier 1: CLI 実行（既定）

#### Step 1: 出力先の用意と疎通確認

**CLI は親ディレクトリを自動作成しない。先に作る。**

```bash
mkdir -p .tmp/ai-review && git check-ignore -q .tmp/ai-review && echo "IGNORED_OK"
```

```bash
codex exec -s read-only -o .tmp/ai-review/probe.md "ゴールは PONG とだけ返すこと。" < /dev/null > .tmp/ai-review/probe.log 2>&1; echo "EXIT=$?"
```

`EXIT=0` かつ出力ファイルに `PONG` が入っていれば疎通OK。失敗理由は `probe.log` に残る。認証エラーならセットアップ案内 → Tier 2 へ。

#### Step 2: レビュー実行

差分レビューはネイティブサブコマンドを使う。

```bash
codex exec -s read-only review -o .tmp/ai-review/diff-review.md --base {ベースブランチ} < /dev/null > .tmp/ai-review/diff-review.log 2>&1; echo "EXIT=$?"
codex exec -s read-only review -o .tmp/ai-review/diff-review.md --uncommitted < /dev/null > .tmp/ai-review/diff-review.log 2>&1; echo "EXIT=$?"
```

> ⚠️ **`review` は対象指定オプションと位置引数プロンプトを併用できない。** 実測で `exit 2`（`the argument '--uncommitted' cannot be used with '[PROMPT]'`）。
> **観点を指定したいレビューは `review` ではなく下記の `codex exec` を使う。**

ファイル単位・観点単位のレビューは `codex exec` を使う。

```bash
codex exec -s read-only -o .tmp/ai-review/review-{観点}.md "$(cat <<'EOF'
ゴールは {対象} を {観点} でレビューし、優先度付きの指摘を返すこと。

【対象ファイル】{ファイルパスを明示列挙。差分レビューなら対象コミット/ブランチも書く}
【観点】{1観点}
【制約】根拠となる行番号を添える。ファイルを実際に読んでから判定する（憶測禁止）
【完了条件】各指摘に 優先度・行番号・内容 が揃っている
【出力形式】テーブル
EOF
)" < /dev/null > .tmp/ai-review/review-{観点}.log 2>&1; echo "EXIT=$?"
```

**対象を必ずプロンプト内で明示する。** `codex exec` は `review` と違い対象を自動判定しないため、対象指定を省くとレビュー範囲が伝わらない。

| 要素 | 理由 |
|------|------|
| `-s read-only` | レビューは読み取りのみ。書き込みが必要な場合だけ明示的に変更する |
| `-o {ファイル}` | **正常終了時に最終メッセージだけ**を保存する。途中経過は残らない。**結果はここから読む** |
| `< /dev/null` | 付けないと stdin を待って停止する |
| `> {ログ} 2>&1` | 進捗ログを捨てずに別ファイルへ。メインを汚さず失敗理由も残る（実測で数百KB） |
| `echo "EXIT=$?"` | 成否判定。**EXIT・ファイル存在・非空**の3点を確認してから読む |

#### Step 3: 分割の要否

**CLI ではタイムアウト由来の強制分割は不要。** ただし次の場合は分割する（並列実行も可）。

- 1リクエストの出力が長すぎて優先度判定が雑になる場合
- 観点ごとに独立した結論が欲しい場合

分割する場合の粒度は「1ファイル / 1観点 / 主張3〜5件」を目安とする。

#### Step 4: リーダー側で統合

各出力ファイルを読んで集約し、1つのレビュー結果にまとめる。結果には**実行経路（CLI / MCP / 利用不可）を明記する**。

### Tier 2: MCP 実行（CLI 不可時のみ・⚠️必ずタスク分割すること）

**`mcp__codex__codex` の1リクエストは数分で MCP タイムアウトする。**
**13視点フルレビュー等の重いタスクを1発で投げると必ずタイムアウトし、出力ファイルも残らず結果を一切回収できない。**
**根本対処は「待つ／リトライ」ではなく「タスク分割で各リクエストをタイムアウト内に収めること」。**

1. **タスク分割を先に設計** — 呼ぶ前に「1ファイル / 1観点 / 主張3〜5件」の分割案を決める。走らせながら考えない
2. **疎通確認 + threadId 取得** — 軽量プロンプト（`Reply with exactly: PONG`）で `mcp__codex__codex` を1回呼ぶ
3. **順次投入** — `mcp__codex__codex-reply` で同一 threadId に小タスクを1件ずつ投入する
   - **結果はテキストで返させる**（タイムアウトするとファイル書き出しも消えるため、ファイル出力に頼らない）
   - 並列が必要な場合のみ threadId を複数立てる
4. **リーダー側で統合** — 各テキスト結果を集約する

補助（第一の対処ではない）: 特定単位がタイムアウトした場合のみ、その単位をさらに細かく分割して再投入する。2回失敗したら Tier 3 へ回す。
**「とにかく待つ」「同じ重いリクエストを3回投げる」のは禁止。**

### Tier 3: フォールバック条件

CLI・MCP のどちらも疎通しない場合、Claude Code のサブエージェントで代替する。

| subagent_type | 用途 |
|--------------|------|
| `codex` | Codex 視点（実務・批判レビュー）の代替 |
| `antigravity` | Antigravity 視点（デザイン・UX）の代替 |
| `universal-security-reviewer` | セキュリティ観点の代替レビュー |
| `universal-performance-analyzer` | パフォーマンス観点の代替レビュー |

**以下を1つのレスポンス内で同時起動する**（逐次実行禁止）。

```markdown
Task(
  subagent_type="codex",
  description="Codex視点レビュー（代替）",
  prompt="
    .claude/skills/code-review/agents/codex-reviewer.md のレビュー観点と、
    .claude/skills/code-review/agents/13-perspectives-unified.md の13視点チェックリストに従い、
    {対象ファイル} を批判的にレビューすること。
  "
)

Task(
  subagent_type="antigravity",
  description="Antigravity視点レビュー（代替）",
  prompt="
    .claude/agents/llm-personas/antigravity.md のペルソナ定義に従い、
    {対象ファイル} をデザイン/UX/視覚階層/情報設計の観点で批判的にレビューすること。
  "
)

Task(
  subagent_type="universal-security-reviewer",
  description="セキュリティ観点レビュー（代替）",
  prompt="{対象ファイル} をセキュリティ観点でレビューすること。"
)
```

`agents/codex-reviewer.md` と `agents/13-perspectives-unified.md` は**手順書・チェックリストの素材**であり、
`subagent_type` として起動できるエージェント定義ではない。
記述規約: [agent-invocation-patterns.md](../../docs/agent-invocation-patterns.md)

Antigravity 用の code-review 固有素材ファイルは**新規作成しない**。`.claude/agents/llm-personas/antigravity.md`（Tier 3 共通のペルソナ定義）をそのまま参照すれば足りる。

Tier 3 は Codex / Antigravity の等価物ではない（同一モデル系による代替で独立性が下がる）。レビュー結果に次を必ず記載する。

```
Codex: 利用不可（CLI / MCP とも疎通せず）。Claude Code の別視点で代替したため、独立性は低下している。
Antigravity: 利用不可（CLI 未設定）。Claude Code の別視点で代替したため、独立性は低下している。
```

## 🟡 Antigravity レビュー（デザイン/UX/情報設計を含むレビューでは必須試行）

**デザイン・UI/UX・視覚階層・情報設計を含むレビューでは、Antigravity（`agy`）による独立レビューを必ず試行すること。**
**それ以外の観点のみのレビューでは任意。** Codex（常に必須試行）とは位置づけが異なる点に注意。

手順の正本は [`ai-cli-execution` スキルの reference.md §6](../ai-cli-execution/reference.md)。本節は要約であり、詳細な実行手順は再掲しない。

### 実行経路の優先順位（CLI > Claude 別視点。MCP 経路なし）

| Tier | 手段 | 使う条件 |
|------|------|----------|
| **1** | **Antigravity CLI**（`agy`） | **既定**。PATH にあり認証済みなら必ずこちら |
| 3 | Claude Code の `antigravity` ペルソナ（`.claude/agents/llm-personas/antigravity.md`） | CLI が使えない場合の代替 |

※ **Antigravity は MCP 経路を持たない。** CLI 不可時は Tier 2 を飛ばして直接 Tier 3 へ落ちる。

### 実行前の確認（Step 0）

```bash
command -v agy && agy --version
```

1. **出力あり** → Tier 1（CLI）でレビューを実行。**モデル指定が必須**: `--mode plan --model gemini-3.1-pro-high`（既定は Gemini 3.6 Flash であり、デザイン/UX の強みを得られない。詳細: reference.md §1・§6 Step 1）
2. **出力なし** → **セットアップ手順を案内**（reference.md §4「Antigravity CLI」のテンプレートをそのまま使用する）してから Tier 3 へ

**判断を仰いで停止しない。** 案内と注記を出したうえで下位 Tier に落として続行する。

### 成功判定の注意（headless の権限モデル）

**`EXIT=0` だけで成功と判定しないこと。** headless 実行では `command`（シェル実行）権限を要するツールが auto-deny され、`EXIT=0` のまま出力が空になることがある。出力ファイルの**非空**を必ず確認する。詳細: reference.md §6「headless の権限モデル」。

### 利用不可の場合の報告（CLI 不可）

**作業を止めない。** 次を報告したうえで Tier 3 に落として継続する。

```
Antigravity が利用できません（CLI 未設定）。
Tier 3（Claude Code の `antigravity` ペルソナ）で継続します。同一モデル系による代替のため、独立性は低下します。

先に Antigravity CLI（agy）を設定して再実行したい場合は、上記セットアップ手順の実施後にレビューを再依頼してください。
```

### 禁止事項

- デザイン/UI/UX/情報設計を含むレビューで Antigravity が利用可能なのにスキップすること
- **CLI 未設定を検出しながら、セットアップ手順を案内せず黙って Tier 3 へ落ちること**
- モデル指定を省略し、既定（Gemini 3.6 Flash）のままデザイン/UX レビューに使うこと
- `EXIT=0` のみで成功と判定すること（権限 auto-deny 時は EXIT=0 かつ出力が空になる）
- プロンプトでシェルコマンドの実行を求めること（headless では auto-deny される）
- Tier を下げた事実を成果物に書かないこと

## 🔴 横断ゲート: 本質ギャルレビュー（必須・全モード共通・Round 1 先頭）

**モードA/Bへ分岐する前に、[essence-gyaru-review](../essence-gyaru-review/SKILL.md) を必ず1回実行すること。skip不可。**

- モードB の4視点・モードA の13視点の**カウントに含めない独立枠**。目的・意思決定・前提・因果・矛盾・業務上の代償・次アクションの7軸で対象を突く
- `review-iteration` は本レビューの周回番号（初回1、再レビューごとに加算）と揃える
- **`code-review` を単体で再実行する場合の `review-iteration` 決定手順**: 同一対象への前回レビューがあれば「前回 `review-iteration` + 1」を使う。前回値は `.tmp/ai-review/gyaru/round-*/report.md` の最大番号等から確認する。前回が存在しない初回は 1 とする
- 出力先: `.tmp/ai-review/gyaru/round-{review-iteration}/report.md`
- essence-gyaru-review の Instructions（Task で `essence-gyaru-reviewer` を起動 → `validate_report.py` で構造検証）に従う
- 全指摘ID（`GYARU-{review-iteration}-{3桁}`）と件数を控え、Round 2（結果統合）・Round 3（fact-check）へそのまま引き渡す

## レビュー視点の階層構造

本スキルには **2つのレベルのレビュー視点** があります：

| レベル | 視点数 | 用途 | 定義場所 |
|--------|--------|------|---------|
| **SKILL.md レベル** | 4視点 | Task 並列実行の単位（モードB） | この SKILL.md 内 |
| **エージェント定義レベル** | 13視点 | コード詳細レビューのチェックリスト | `agents/13-perspectives-unified.md` |

**関係性:**
- **4視点**（技術品質 / セキュリティ / ドキュメント整合性 / ユーザー視点）は、Codex が利用できない場合の **モードB** で Task を並列起動する単位
- **13視点**（Readability / Naming / Error Handling / ... / Business Logic）は、エージェント定義 `13-perspectives-unified.md` で定義される **コードレビューの詳細チェック項目**
- モードA（Codex 利用可能時）では、13視点エージェントと Codex を並列実行する

**モードA の観点割り当て**（強みに合わせて分ける。詳細: `.claude/docs/ai-cli-execution-policy.md` §1）

| 実行主体 | 割り当てる観点 |
|---------|---------------|
| Codex CLI | 正確性 / バグ / セキュリティ / 実行可能性 / 事実誤認の摘発 |
| Antigravity CLI（`agy`。利用可能時） | UI / UX / 視覚階層 / 情報設計 / 図表・構造の見通し |
| Claude Code 13視点エージェント | 上記以外の全観点 + プロジェクト固有規約の適合 + 結果統合 |

両者が同じ問題を指摘したら信頼度が上がる。片方だけの指摘は Round 3（`code-review-fact-check`）で事実照合する。

## 並列実行方法（必須手順）

### Step 1: レビュー対象ファイルを特定

```bash
# 変更ファイルを確認
git status
git diff --name-only
```

### Step 2: 4並列 Task を起動

**必ず1つのメッセージ内で4つの Task tool を同時に呼び出すこと。**

```
Task 1: 技術品質レビュー
Task 2: セキュリティレビュー
Task 3: ドキュメント整合性レビュー
Task 4: ユーザー視点レビュー
```

### Step 3（Round 2）: 結果統合

4つの Task の結果と、横断ゲートで得た本質ギャルレビューの全指摘IDを合わせて、以下のテンプレートで統合結果を出力する。ギャル指摘は4視点/13視点のカウントに含めず、統合レビュー結果に別枠として記載する。

### Round 3: ファクトチェック（必須）

結果統合（Step 3）が完了したら、統合レビュー結果をそのまま最終成果物にせず、必ず [code-review-fact-check スキル](../code-review-fact-check/SKILL.md) を Round 3 として実行し、実コード照合で「妥当/部分的に妥当/過剰/事実誤認」を判定すること。GYARU-* を含む全指摘が検証対象。

```
Round 1: 本質ギャルレビュー（横断ゲート・必須）+ Claude Code 4視点並列レビュー（モードB）/ Codex 独立レビュー（モードA）
Round 2: 結果統合（Step 3, 上記。ギャル指摘IDも保持）
Round 3: code-review-fact-check スキルでファクトチェックを実施（GYARU-* を含む全指摘）← 必須・省略禁止
```

ファクトチェックで「妥当」と判定された指摘のみを最終 PR コメント・レビュー結果に採用する。詳細な実行手順（4 Phase・4択判定区分・出力テンプレート）は `code-review-fact-check/SKILL.md` を参照。

## レビューの姿勢（絶対ルール）

**レビューは時間がかかっても構わない。網羅性が最も大事。**

| 原則 | 説明 |
|------|------|
| **時間をかけてよい** | レビューに時間がかかることは問題ではない。急いで見落とすほうが問題 |
| **網羅性が最優先** | 軽微な問題も含めて全て洗い出す。「些細だから」で見逃さない |
| **全ファイルを確認** | 変更があったファイルだけでなく、影響範囲のファイルも確認する |
| **Codex は必ず試行** | 経路は CLI > MCP > Claude 別視点。CLI が使えるのに MCP を選ばない。CLI 未設定時はセットアップ手順を案内してからフォールバックする（詳細は「Codex 実行」セクション） |
| **Antigravity はデザイン/UX/情報設計を含むレビューで必ず試行** | 経路は CLI > Claude 別視点（MCP 経路なし）。CLI 未設定時はセットアップ手順を案内してから Tier 3 へ落とす（詳細は「Antigravity レビュー」セクション） |

---

## 批判的レビューの原則（必須）

**レビューは批判的に行うこと。**

| 原則                       | 説明                                               |
| -------------------------- | -------------------------------------------------- |
| **問題を探す姿勢**         | 「問題がない」ではなく「問題を見つける」姿勢で臨む |
| **仮定を疑う**             | 実装者の仮定・前提条件が正しいか検証する           |
| **エッジケースを想定**     | 正常系だけでなく異常系・境界値を重点的に確認       |
| **セキュリティ最優先**     | 脆弱性がないか徹底的に調査する                     |
| **ビジネスロジックの正しさ** | 金額計算、状態遷移、外部データ変換が仕様通りか検証 |

**禁止事項:**

- 「問題ありません」で終わらせない
- 表面的な確認で済ませない
- 実装者の意図を無条件に信用しない

## レビューコメントの優先度

| 優先度   | 記法       | 説明                             |
| -------- | ---------- | -------------------------------- |
| 必須対応 | `[MUST]`   | マージ前に必ず修正が必要         |
| 推奨     | `[SHOULD]` | 修正が望ましいが、理由があればOK |
| 提案     | `[NIT]`    | 細かい指摘、対応は任意           |
| 質問     | `[Q]`      | 意図の確認、理解のための質問     |
| 称賛     | `[GOOD]`   | 良い実装へのコメント             |
