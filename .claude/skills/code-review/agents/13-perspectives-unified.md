# 統一13視点レビュー定義

## 概要

Go バックエンドと Next.js フロントエンド両方に適用可能な13視点レビューの統一定義。
Claude Code と Codex（CLI / MCP）の両方で使用する。

Auth の「アクセスゲートの例外」、Test Quality の「テスト凍結・放置FAIL」、Error Handling の「コードの一意性」、
Business Logic の「画面遷移・導線の仕様適合」は、**レビューをすり抜けた実バグの事後分析（2026-07）から追加した項目**である。
一般論ではなく実際に取り逃した型なので、削らずに残すこと。

---

## 13視点詳細

### 1. Readability（可読性）

| 項目 | Go | Next |
|------|-----|------|
| フォーマット | `gofmt` 準拠 | ESLint/Prettier 準拠 |
| ドキュメント | GoDoc コメント | JSDoc / TSDoc |
| 関数長 | 50行以下推奨 | 30行以下推奨 |
| 複雑度 | 認知的複雑度 10以下 | 認知的複雑度 10以下 |

**チェックポイント:**
- [ ] コードが自己文書化されているか
- [ ] 複雑なロジックにコメントがあるか
- [ ] 一貫したインデントとフォーマットか

---

### 2. Naming（命名規則）

| 項目 | Go | Next |
|------|-----|------|
| 変数 | camelCase / MixedCaps | camelCase |
| 定数 | MixedCaps | UPPER_SNAKE_CASE |
| 型/構造体 | MixedCaps | PascalCase |
| 関数 | MixedCaps（公開）/ camelCase（非公開） | camelCase |
| コンポーネント | - | PascalCase |
| フック | - | use + PascalCase |

**チェックポイント:**
- [ ] 名前が意図を明確に表しているか
- [ ] 略語は一般的に理解可能か
- [ ] プロジェクト全体で一貫しているか

---

### 3. Code Structure（コード構造）

| 項目 | Go | Next |
|------|-----|------|
| ファイルサイズ | 300行以下 | 200行以下 |
| 関数サイズ | 50行以下推奨 | 30行以下推奨 |
| 層分離 | controller/model/helper | page/component/service |
| 単一責任 | 1ファイル1責任 | 1コンポーネント1責任 |

**チェックポイント:**
- [ ] ファイルが肥大化していないか
- [ ] 責任が明確に分離されているか
- [ ] 循環依存がないか

---

### 4. Input Validation（入力検証）

| 項目 | Go | Next |
|------|-----|------|
| DB操作 | Squirrel必須（生SQL禁止） | - |
| バリデーション | 構造体タグ / カスタムバリデータ | Zod / yup |
| XSS対策 | `html.EscapeString()` | `dangerouslySetInnerHTML` 禁止 |
| SQLi対策 | プリペアドステートメント | - |
| パストラバーサル | `filepath.Clean()` + 基準ディレクトリ配下の確認 | `path.resolve()` 後に基準ディレクトリ配下か確認 |
| SSRF | 許可リスト + 内部IP遮断（詳細: security スキル A10） | 同左 |
| デシリアライズ | 型を限定（`any` への復元禁止） | `JSON.parse` 後の型検証 |

**チェックポイント:**
- [ ] 外部入力を信頼していないか
- [ ] バリデーションエラーが適切に処理されているか
- [ ] エスケープ処理が漏れていないか
- [ ] 危険な操作（SQL発行・シェル実行・パス生成・外部リクエスト）まで到達する経路を追ったか
- [ ] 同じ危険操作を呼ぶ箇所が他にもないか（1件見つけて終わりにしない）

---

### 5. Auth（認証・認可）

| 項目 | Go | Next |
|------|-----|------|
| 認証確認 | ミドルウェアで検証 | useAuth / 保護ルート |
| 認可チェック | テナント分離・リソースアクセス制御 | usePermission |
| トークン管理 | 暗号化して保存 | HttpOnly Cookie |
| CSRF対策 | トークン検証 | X-CSRF-Token ヘッダー |
| 更新フィールド制限 | 更新可能フィールドを許可リストで限定 | 同左 |

**チェックポイント:**
- [ ] 全ての保護エンドポイントで認証確認しているか
- [ ] テナント分離が適切か（他社データにアクセスできないか）
- [ ] トークンが安全に保存されているか
- [ ] アクセスゲートの例外（無料枠・トライアル・管理者バイパス等）が意図した対象だけを通しているか
- [ ] 自己申告で更新するAPIで `role` / `tenant_id` 等の権限フィールドを書き換えられないか
- [ ] 検証したオブジェクトと実際に使うオブジェクトが同一か（検証後に別の値を使っていないか）

---

### 6. Query Efficiency（クエリ効率）

| 項目 | Go | Next |
|------|-----|------|
| N+1問題 | ループ内クエリ禁止 | SWR キャッシュ活用 |
| インデックス | WHERE句にインデックス確認 | - |
| ページネーション | LIMIT/OFFSET 使用 | 無限スクロール / ページング |
| キャッシュ | 必要に応じてRedis等 | SWR / React Query |

**チェックポイント:**
- [ ] ループ内でDB/APIクエリを発行していないか
- [ ] 大量データ取得時にページネーションがあるか
- [ ] 適切にキャッシュが活用されているか

---

### 7. Memory（メモリ・並行）

| 項目 | Go | Next |
|------|-----|------|
| メモリリーク | defer でリソース解放 | useEffect クリーンアップ |
| 並行処理 | goroutine リーク防止 | - |
| 競合状態 | mutex / sync.Map | - |
| メモ化 | - | useMemo / useCallback |

**チェックポイント:**
- [ ] リソースが適切に解放されているか
- [ ] goroutine / useEffect がクリーンアップされているか
- [ ] 不要な再計算・再レンダリングがないか

---

### 8. Test Coverage（テストカバレッジ）

| 項目 | Go | Next |
|------|-----|------|
| テストフレームワーク | testing パッケージ | Jest / Testing Library |
| カバレッジ目標 | 主要パス 80%以上 | 主要パス 70%以上 |
| テスト種別 | ユニット + 統合 | ユニット + E2E |

**チェックポイント:**
- [ ] 主要機能にテストがあるか
- [ ] エッジケースがカバーされているか
- [ ] テストが実行可能か（壊れていないか）

---

### 9. Test Quality（テスト品質）

| 項目 | Go | Next |
|------|-----|------|
| テスト方針 | ブラックボックス | ブラックボックス |
| 対象 | 公開インターフェースのみ | 公開インターフェースのみ |
| 観点 | 入出力、異常系、境界値 | ユーザー操作、表示結果 |
| アサーション | 具体的な期待値 | 具体的な期待値 |
| 更新条件 | 仕様変更時のみ（テスト凍結） | 仕様変更時のみ（テスト凍結） |
| 無効化 | `t.Skip` / 放置 FAIL を残さない | `it.skip` / `.only` / 放置 FAIL を残さない |

**チェックポイント:**
- [ ] 内部実装に依存していないか
- [ ] 異常系・境界値をテストしているか
- [ ] テスト名が意図を明確に表しているか
- [ ] 期待値を実装に合わせて書き換えていないか（テスト＝仕様。変更は仕様変更時のみ）
- [ ] スキップ・放置 FAIL がないか。テスト実行自体が CI / hooks でコメントアウトされ無効化されていないか

---

### 10. API Design（API設計）

| 項目 | Go | Next |
|------|-----|------|
| 設計原則 | RESTful | - |
| ドキュメント | OpenAPI 同期必須 | 型定義と同期 |
| バージョニング | URL or ヘッダー | - |
| レスポンス形式 | 統一された JSON 構造 | 型安全な fetch |

**チェックポイント:**
- [ ] API仕様とコードが一致しているか
- [ ] エンドポイント変更時にドキュメント更新したか
- [ ] エラーレスポンスが統一されているか

---

### 11. Dependency（依存関係）

| 項目 | Go | Next |
|------|-----|------|
| DI | コンストラクタインジェクション | Props / Context |
| 抽象化 | インターフェース定義 | 型定義 |
| 疎結合 | 具象型に依存しない | コンポーネント分離 |

**チェックポイント:**
- [ ] 依存関係が明示的に注入されているか
- [ ] テスト時にモック可能な設計か
- [ ] 不要な依存がないか

---

### 12. Error Handling（エラーハンドリング）

| 項目 | Go | Next |
|------|-----|------|
| ログ | 構造化ログ必須 | console 禁止 |
| エラー伝播 | エラーラップ | Error Boundary |
| ユーザー表示 | 適切なエラーメッセージ | ローディング/エラー状態 |
| リトライ | 適切なリトライ戦略 | fetch リトライ |
| コードの一意性 | 原因ごとに区別できる情報を持たせる（認証・認可・存在確認は例外。下記参照） | 同左 |

**チェックポイント:**
- [ ] エラーが適切にログ出力されているか
- [ ] ユーザーに理解可能なメッセージを表示しているか
- [ ] エラー時にアプリがクラッシュしないか
- [ ] 同一コード・同一メッセージで異なる原因を兼用していないか（例: 権限不足の 403 とリソース非公開の 403、認証切れの 401 とトークン形式不正の 401）。**ただし認証・認可・存在確認に関わるエラー（ログイン失敗・権限不足・リソースの非公開/非存在）はユーザー向けメッセージを意図的に汎化し、原因の区別はサーバ側ログや内部エラーコードなど攻撃者が観測できない経路にのみ持たせる**（ユーザー列挙・内部状態の推測を防ぐため）

### 13. Business Logic（ビジネスロジック）

> **この視点はプロジェクト固有のビジネスルールに依存します。**
> プロジェクトごとにチェック項目をカスタマイズしてください。
> 以下は汎用的なチェック項目のテンプレートです。

#### バックエンド重点チェック

| # | チェック項目 | 確認内容 | 重要度 |
|---|------------|----------|--------|
| 1 | 金額・数値計算の正確性 | 外部システムから取得した値を再計算していないか。配分済み・計算済みの値をそのまま使用しているか | 高 |
| 2 | 税・料金処理の正確性 | 税区分・料金区分に基づく正しい値の選択が行われているか | 高 |
| 3 | 特殊処理の規則 | 返品・キャンセル・割引等の特殊ケースで符号・区分値が正しいか | 高 |
| 4 | 外部データ再計算禁止 | 外部システム（EC/POS/決済等）の値をそのまま使用し、加工・丸め処理をしていないか | 高 |
| 5 | マッピング・変換の正確性 | マスタデータに基づく変換を使用し、デフォルト値フォールバックを禁止しているか | 高 |
| 6 | 状態遷移の整合性 | 業務フロー（例: 注文→出荷→完了）に沿った遷移のみ許可されているか | 高 |

#### フロントエンド重点チェック

| # | チェック項目 | 確認内容 | 重要度 |
|---|------------|----------|--------|
| 1 | 金額表示の正確性 | APIから受け取った金額をそのまま表示し、フロント側で再計算していないか | 高 |
| 2 | 税込/税抜の表示 | 区分に応じた正しい金額が表示されているか | 高 |
| 3 | 状態遷移の制御 | 業務フロー上許可されない操作ボタンが無効化されているか | 高 |
| 4 | 条件分岐の網羅性 | 返品、キャンセル、部分処理等の特殊ケースが考慮されているか | 高 |
| 5 | データ変換・フォーマット | 数値の丸め、日付フォーマット、通貨表示が業務要件に合致しているか | 中 |
| 6 | バリデーションの業務適合性 | 入力制約（数量上限、金額範囲等）が業務ルールに合致しているか | 中 |
| 7 | 画面遷移・導線の仕様適合 | 遷移先・導線が仕様書/チケットの記載どおりか。実装同士の整合ではなく**仕様との整合**を問う | 高 |

**チェックポイント:**
- [ ] 金額計算がAPIの値をそのまま使用しているか（再計算していないか）
- [ ] 税・料金区分に基づいて正しい値が選択されているか
- [ ] 返品・キャンセル等の特殊ケースが正しく処理されているか
- [ ] 状態遷移が業務フローに沿っているか
- [ ] 外部データの変換・マッピングが正確か
- [ ] 画面遷移・導線が仕様書/チケットの記載どおりか（実装が「動く」ことと「仕様通り」は別）

## 品質ゲート（sonnet-uplift）— Business Logic 視点限定

Business Logic 視点（金額・税・状態遷移等の業務仕様判定）は、外部の業務要件を推測で断定すると誤指摘・見落としの両方でリスクが大きい。
sonnet モデルでこの視点を判定する際は、以下のゲートを必ず通す。

### 完了条件チェックリスト

出力を返す前に、以下を全て満たすことを確認する:

- [ ] 金額・税・状態遷移に関する各チェック項目（1-6）についてOK/WARN/NG/要親判断のいずれかを判定している
- [ ] フロントエンド重点チェック項目7（画面遷移・導線の仕様適合）について、仕様書/チケットの記載が確認できない場合は OK と断定せず「要親判断」としている
- [ ] 「要親判断」とした項目には、判断できない理由（業務仕様書の不在・外部システム仕様の未確認等）を具体的に記載している
- [ ] コード上は正しく見えるが業務ルールの正否に確信が持てない場合、OK/NGを断定せず必ず「要親判断」としている
- [ ] 外部データの再計算・丸め処理を検出した場合、それが業務要件として許容されるか判断できないときは「要親判断」としている
- [ ] 「要親判断」が1件でもある場合、総合評価をPASSにはせず必ずWARN以上として明示している（放置してマージ可としない）

### 自己検証ループ

1. Business Logic 視点のドラフト判定を作成する
2. 完了条件チェックリストと照合する
3. NG項目があれば修正して再照合する（最大2周）
4. 2周で収束しない場合はエスカレーションする

### エスカレーション基準

以下のいずれかに該当する場合、自力で断定せず、出力の冒頭に次の形式で返す:

- 自己検証ループ2周でチェックリストが収束しない
- チェックリストにないトレードオフ判断が必要になった
- 不可逆操作・対外公開・機密・法務/人事に関わる判断が必要になった
- 業務仕様（税区分・状態遷移フロー等）の正否について、コード読解だけでは確信を持てない項目が1件以上ある

```
ESCALATION: {理由を1文}
完了済み: {完了した視点・判定}
残作業: {要親判断とした項目一覧}
判断材料: {親が判断するために必要な情報（該当コード箇所・業務仕様が不明な理由）}
```

### 既知の失敗パターン

- 業務仕様の正否に確信がないまま「OK」と楽観判定し、実際は不正な状態遷移を見逃す
- 逆に確信がないまま「NG」と過剰指摘し、レビュー対象者の手戻りを増やす

## Codex プロンプトテンプレート

> **経路は CLI が既定**（`codex exec -s read-only -o {出力ファイル}`）。詳細は [`.claude/docs/ai-cli-execution-policy.md`](../../../docs/ai-cli-execution-policy.md) を参照。
> CLI では強制分割は不要だが、観点ごとに独立した結論が欲しい場合は視点単位で切り出して並列実行してよい。
> **⚠️ MCP 経路（CLI 不可時）では、13視点を1発でまとめて投げないこと。** 1リクエストは数分でタイムアウトする。
> その場合は観点を1件ずつ（または1ファイル単位で）分割し、`mcp__codex__codex-reply` で順次投入すること。
> 以下のテンプレートは観点全体の一覧であり、分割時は各視点を切り出して投入する。
> **投入する各プロンプトは冒頭で「ゴールは〜」と成果を明示すること**（設計ルール: [`.claude/docs/codex-prompt-guideline.md`](../../../docs/codex-prompt-guideline.md)）。

```markdown
| 1 | 高/中/低 | path:123 | {視点名} | {内容} | {該当コードの引用} | {誰が何をできるか} | {具体的な直し方} |

### 総合評価: PASS / WARN / NG
```

**優先度が「高」の指摘には、根拠・影響・修正案の3列を必ず埋める。**
`path:123` だけでは受け取った側が踏めるかどうかを判断できない。

| 列 | 書く内容 |
|----|---------|
| 根拠 | 該当コードの引用。入力の発生源から危険な操作まで複数箇所にまたがる場合は経路を示す |
| 影響 | 誰が・どんな前提条件で・何ができるか（「危険」ではなく具体的な結果） |
| 修正案 | 具体的な直し方。再発防止のテストが書けるなら併記する |

セキュリティ指摘の妥当性判定（経路・境界・反証）は [code-review-fact-check](../../code-review-fact-check/SKILL.md) が担う。
実装前の脅威モデリングは [security スキル](../../security/SKILL.md) の A04 を参照。

## 判定基準

| 評価 | 基準 |
|------|------|
| **OK** | 問題なし、または軽微な改善提案のみ |
| **WARN** | 対応推奨だが、マージ可能 |
| **NG** | マージ前に必ず修正が必要 |
| **要親判断** | （Business Logic 視点のみ）業務仕様の正否に確信が持てず断定不可。親セッションの判断に委譲 |

### 総合評価

| 総合 | 条件 |
|------|------|
| **PASS** | 全視点が OK または WARN（要親判断なし） |
| **WARN** | 1つ以上の WARN または要親判断あり、NG なし |
| **NG** | 1つ以上の NG あり |
