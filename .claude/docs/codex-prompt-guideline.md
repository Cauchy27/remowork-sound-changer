# Codex プロンプト設計ガイドライン

Codex（`codex exec` CLI / `mcp__codex__codex` / `mcp__codex__codex-reply`）へプロンプトを生成する際の共通ルール。MCP のツール名は Claude Code が実行役の場合の名前で、他の実行役は [ai-cli-execution/reference.md](../skills/ai-cli-execution/reference.md)「実行役ごとの読み替え」節で読み替える。
**レビュー依頼・実装依頼・調査依頼など、Codex に指示を出す全ての場面に適用する。**

> どの経路で Codex を呼ぶか（CLI > MCP > 親セッション上の別視点）は [外部AIツール実行ポリシー](ai-cli-execution-policy.md) を参照。本ドキュメントはプロンプトの中身のみを扱う。

> 想定読者: Codex を**呼び出す側**（プロンプトを生成する AI・人間）。Codex 自身が本ドキュメントを読んだ場合は、受け取るプロンプトがこの形式で来ることの説明として扱えばよく、自身の応答形式を変える必要はない。

---

## 🔴 絶対ルール: ゴールを冒頭で明示する

Codex へのプロンプトは、**必ず冒頭に「ゴールは〜」で始まる1文**を置き、達成すべき成果を明確に指示する。

| 原則 | 説明 |
|------|------|
| 成果で書く | 手段ではなく成果を書く。「〜を調べて」ではなく「ゴールは {対象} の {観点} を判定し指摘リストを返すこと」 |
| 検証可能に書く | 判定基準・件数・出力形式を含め、Codex 自身が完了を判断できる形にする |
| 1リクエスト1ゴール | 複数ゴールを1プロンプトに詰めない。分割して順次投入する |

---

## 🔴 絶対ルール: モデル役割分担ブロックを必ず入れる

Codex へのプロンプトには、**下記の【モデル運用】ブロックを原文のまま必ず含める**。ゴール文の直後に置く。

```text
<!-- codex-prompt-model-ops:start -->
【モデル運用】
- あなた（GPT-6.1-Sol / reasoning effort: xhigh）は監督役。xhigh では自動委託（proactive delegation）が効かないため、委託が必要な作業（呼出元の指示、または AGENTS.md の委託条件に該当する作業）は自分でサブエージェントを明示起動する。それ以外の精読・判定・実作業は自分で直接行う
- サブエージェントを明示的に起動する時は、**モデルと reasoning effort を必ずセットで指定する**。解決順は「明示指定 > `[agents]` 既定 > 親の値」で、モデルだけ指定すると effort はそのモデルの既定（GPT-6.1-Sol なら `low`）へ落ちる。省略時にどこへ落ちるかを推測で決めない
- 大きな問題（設計上の欠陥・原因不明の不具合・広範囲に影響する仕様矛盾）を見つけた時は、個別のサブエージェント（GPT-6.1-Sol / reasoning effort: max）を起動し、調査・修正させる
- reasoning effort に `none` は使わない（GPT-6.1-Sol は非対応）
<!-- codex-prompt-model-ops:end -->
```

### 理由

| 項目 | 内容 |
|------|------|
| 委託は明示起動 | 自動委託（automatic task delegation）は `xhigh` には付かない（`~/.codex/models_cache.json` でこの説明が付くのは最上位 effort だけ）。監督役が委託したい作業はサブエージェントを明示起動して振り分ける |
| 解決順の落とし穴 | サブエージェントの model / effort は「明示指定 > `[agents]` 既定 > 親の値」の順で解決され、モデルだけ指定すると effort はそのモデルの既定（GPT-6.1-Sol なら `low`）へ落ちる。セット指定を必須にしないと深掘り用のサブエージェントが `low` で動く |

### 前提

| 項目 | 内容 |
|------|------|
| 対象モデル識別子 | `gpt-6.1-sol`（対応 effort: low / medium / high / xhigh / max に加えて ultra。本運用の既定は `xhigh`。別の effort は依頼者が明示した個別実行に限り、実行記録に残す。モデル自体の既定は `low`。`none` 非対応） |
| 「xhigh」の意味 | `gpt-6.1-sol` を reasoning effort `xhigh` で動かす指定。自動委託は付かないため、委託は監督役の明示起動で行う |
| 親セッションのモデル | `~/.codex/config.toml:2-3` の `model = "gpt-6.1-sol"` / `model_reasoning_effort = "xhigh"` 固定（実測値）。判断 #4（2026-09-18）・D1（2026-09-24）で既定を xhigh に確定。モデルは 2026-10-11 にオペレーター指示で GPT-6-Astra から GPT-6.1-Sol へ変更。実測 2026-10-11（Codex CLI 0.162.1。`codex exec -s read-only -m gpt-6.1-sol -c 'model_reasoning_effort="xhigh"'` の起動成功と、ログの `model: gpt-6.1-sol` / `reasoning effort: xhigh` を確認）。**プロンプト側で親モデル・effort を切り替えない** |
| サブエージェントの解決順 | 明示指定 > `[agents]` 既定（`agents.default_subagent_model` / `agents.default_subagent_reasoning_effort`）> 親の値。モデルだけ指定すると effort はそのモデルの既定へ落ちる。model だけ設定した custom agent は解決済み effort を保持する（出典: https://learn.chatgpt.com/docs/agent-configuration/subagents ） |
| `[agents]` 既定 | 現行 `~/.codex/config.toml` には未設定（model・effort とも省略した場合は親の `gpt-6.1-sol` / `xhigh` を継承） |
| 専用サブエージェント定義 | **不要**。Codex 側の標準サブエージェント機構をそのまま使う |
| CLI 要件 | 利用するCLIで対象モデル・effortが認識され、起動が成功することを確認する。バージョン文字列だけで対応を保証しない。更新実測は log.md に記録する |

Work と local Codex では利用可能なサブエージェント機構や適用指示が異なる。effort の説明だけで委託可能とみなさず、その実行環境で機構が有効か、委託条件が許可されているかを確認する。このブロックを流用する際もモデル・effortのセット指定と大きな問題時の明示起動条件を維持し、親セッションの設定を変更しない。

> ⚠️ 本ブロックは恒久ルールだが、「その他の注意点」#5（恒久ルールは `AGENTS.md` へ）の例外として**毎回プロンプトに書く**。サブエージェントの model / effort セット指定と `none` 禁止はセッション冒頭で効かせないと、深掘り用のサブエージェントが `low` で走り始めてから是正できないため。

## 🔴 絶対ルール: スコープを固定し過剰処理を防ぐ

Codex はゴールへの執着が強く、放置すると**依頼していない周辺まで直しにいく**。
下記の【スコープ】ブロックを、ゴール文・【モデル運用】に続けて必ず含める。

```text
<!-- codex-prompt-scope:start -->
【スコープ】
- ゴールに直接必要な変更だけを行う。ついで修正・周辺リファクタ・体裁調整・命名の統一は行わない
- ゴールの前提に矛盾・欠落を見つけたら、結果を左右する未決事項に依存する作業だけ保留し、独立部分は進める。保留事項は根拠・影響・止まる工程とともに最後にまとめる。勝手に補完・拡大解釈しない
- 着手前に次の3点を自己確認する。答えられない項目が結果を左右する場合は質問を返し、独立部分は進める
  1. 目的: この作業は何のためか。誰の何が変わるか
  2. 代償: この変更で失われるもの・増える運用負荷は何か
  3. 停止条件: どこまでやったら完了か。それ以上やらない線はどこか
<!-- codex-prompt-scope:end -->
```

### 3点の自己確認は本質ギャルレビューの圧縮版

上記3点は `essence-gyaru-review` の7軸（目的 → 意思決定 → 前提 → 因果 → 矛盾 → 業務上の代償 → 次アクション）のうち、
**着手前に効かせないと手遅れになる軸**（目的・代償・次アクション）を Codex 向けに圧縮したもの。

| 使い分け | 手段 |
|---------|------|
| Codex に**着手させる前**の暴走抑止 | 本ブロック（プロンプトへ埋め込む） |
| Codex の**成果物**に対する本質検証 | `essence-gyaru-review` スキルを別途起動する（code-review では Round 1 先頭の横断ゲートとして実行済み） |

**両者は代替関係ではない。** プロンプト側のブロックは「やりすぎを起こさせない」ための事前制御、
ギャルレビューは「出てきたものが目的に適っているか」の事後検証であり、片方では他方を代替できない。

### ゴール文の書き方（過剰処理を防ぐ観点から）

| NG | 理由 | OK |
|----|------|-----|
| 「〜を改善すること」 | 改善の終わりが定義されず、際限なく手を広げる | 「〜の {具体的な指標} を {基準} まで満たすこと」 |
| 「〜を確認し、必要なら修正すること」 | 「必要なら」の判断が Codex に委ねられ、スコープが無限化する | 「〜を確認し、指摘リストを返すこと。修正は行わない」 |
| 「〜をリファクタすること」 | 対象範囲が無い | 「{ファイル} の {関数} を、外部I/Fを変えずに {条件} を満たす形へ書き換えること」 |

## 🔴 絶対ルール: レビュー・修正ループの粒度を固定する

Codex は指示がないと**変更のたび・ファイル追加のたびにレビューを回す**。
1回の追加ごとにレビューが走ると実装が前に進まず、レートリミットだけが消える。
**実装依頼・修正依頼を出す全プロンプトに、下記の【レビュー粒度】ブロックを原文のまま必ず含める。**【スコープ】に続けて置く。

```
【レビュー粒度】
- 実装 → レビュー → 修正のループは「1ページ / 1機能」単位でのみ回す。ファイル追加・関数追加・小修正のたびに回さない
- レビューは実装単位が動作する状態に達した時点で1回だけ実行する。実装途中の中間状態ではレビューを起動しない
- 指摘は P0（ブロッカー）/ P1（要修正）/ P2（軽微）に分類し、修正するのは P0・P1 のみ。P2 は記録して次の単位へ進む
- 修正後の再確認は修正差分に限定する。単位全体のレビューをやり直さない
- コミットは元ユーザーが明示依頼した場合のみ、その依頼範囲内で行う。この定型ブロック自体を承認とみなさない。依頼がなければ各単位を検証済み・未コミットで完了し、次の単位へ進む
```

### 粒度の定義（レビュー単位 = 1ページ / 1機能）

| 種別 | 1単位に含めるもの |
|------|-----------------|
| 画面（ページ） | 画面 + API 接続 + その画面の対象テスト |
| 機能（画面をまたぐ） | 機能に属する全画面・全エンドポイント + 対象テスト |
| API 単体（画面なし） | 関連エンドポイント群 + スキーマ/型 + 対象テスト |
| バグ修正 | 該当バグの修正 + 回帰テスト |

正本は `impl-review-loop` スキル の「レビュー粒度」セクション。
本ブロックはその内容を Codex プロンプトへ埋め込むための圧縮版であり、判断が割れた場合は impl-review-loop を正とする。

### 「タスク分割」との違い（混同禁止）

| 項目 | 何を分割するか | 目的 |
|------|--------------|------|
| タスク分割（下記「その他の注意点」#1） | **1リクエストで投げる依頼の量** | MCP 経路のタイムアウト回避・出力の粒度制御 |
| レビュー粒度（本節） | **ループを回す頻度** | 過剰レビューによる停滞の防止 |

**依頼を細かく分けても、レビューは実装単位ごとに1回。** 分割したリクエストごとにレビューを回さない。

## プロンプト4要素（OpenAI 公式ガイド準拠）

効果的な Codex プロンプトは以下の4要素で構成する。

| # | 要素 | 内容 | 必須度 |
|---|------|------|--------|
| 0 | モデル運用（Model ops） | 本書の正本ブロックを送信前にゴール文直後へ展開し、実際の送信本文で確認 | 必須 |
| 1 | ゴール（Goal） | 何を達成するか。成果・アウトカムで記述。「改善」「必要なら修正」など終端の無い書き方をしない | 必須 |
| 1.5 | スコープ（Scope） | 本書の正本ブロックをモデル運用に続けて展開し、実際の送信本文で確認 | 必須 |
| 1.6 | レビュー粒度（Review granularity） | ループを回す単位を「1ページ / 1機能」に固定する。上記「絶対ルール」のブロックを原文のまま記載 | 実装・修正依頼では必須（レビュー専用依頼では不要） |
| 2 | コンテキスト（Context） | 対象ファイルパス・関連ドキュメント・エラー内容・背景 | 必須 |
| 3 | 制約（Constraints） | 従うべき規約・変更禁止事項・レビュー観点・件数上限 | 必要時 |
| 4 | 完了条件（Done when） | 完了と判定できる検証可能な条件（テスト成功・指摘形式充足等） | 必須 |

## その他の注意点（Codex に指示する際の必須チェック）

| # | 注意点 | 理由 |
|---|--------|------|
| 1 | **タスク分割**: 1リクエスト = 1ファイル / 1観点 / 根拠のある主張0〜5件 | **MCP 経路では必須**（数分でタイムアウトするため分割が根本対処）。CLI 経路では強制ではなく、観点ごとに独立した結論が欲しい場合の任意分割。**分割するのは依頼の量であって、レビューを回す頻度ではない**（上記「レビュー・修正ループの粒度を固定する」参照） |
| 2 | **結果の受け取り方を経路で変える** | MCP はテキストで返させる（タイムアウト時にファイル書き出しも消えるため）。CLI は `-o {ファイル}` で回収し、メインコンテキストへ生ログを流さない |
| 3 | **出力形式を明示する** | テーブル・OK/WARN/NG 等を指定しないと集約コストが跳ね上がる |
| 4 | **憶測回答の禁止を明示する** | 「対象ファイルを実際に読んでから回答すること」を必ず書く |
| 5 | **恒久ルールはプロンプトに詰めない** | 毎回変わらない規約は `AGENTS.md` に置く。プロンプトはタスク固有情報に絞る |
| 6 | **曖昧なタスクは先に計画を出させる** | 実装依頼が曖昧な場合、まず計画のみ返させてから実装を投入する |
| 7 | **検証手順を含める**（実装依頼時） | 再現手順・lint・テスト実行を指示すると出力品質が上がる（公式明記） |

## 正本ブロックを送信本文へ展開する

【モデル運用】【スコープ】の原文は本書のマーカー内だけで管理する。各テンプレートの `{{CODEX_GUARD_BLOCKS}}` は、送信前にこの2ブロックの全文へ置き換えるための記号であり、そのまま送らない。順序は「冒頭のゴール文 → モデル運用 → スコープ → タスク固有本文」。実装・修正依頼は続けて【レビュー粒度】も原文で含める。

### Bash・標準シェルでの組立と確認

対象リポジトリのルートで、実行ごとの出力先ディレクトリ `REVIEW_DIR`（作り方と理由は [ai-cli-execution/reference.md](../skills/ai-cli-execution/reference.md) §3）を用意してから以下を実行する。起動前に有料 API への接続確認を行う（同 §3「有料 API への接続確認」）。Claude Code が実行役なら、`codex exec` は Bash の背景実行で起動する（同 §3「長時間の CLI 実行」）。`awk` はマーカーの欠落・重複・順序不正を拒否し、原文を加工せず取り出す。ゴールとタスク本文は引用 heredoc に置き、原文は `printf` で挿入する。バッククォート・`$()`・変数文字列を再評価する `eval` や引用なしの heredoc は使わない。

```bash
REVIEW_DIR="{用意した REVIEW_DIR}"
codex_guard_blocks=$(awk '
$0 == "<!-- codex-prompt-model-ops:start -->" { if (step != 0) exit 1; step=1; next }
$0 == "<!-- codex-prompt-model-ops:end -->" { if (step != 1) exit 1; step=2; print ""; next }
$0 == "<!-- codex-prompt-scope:start -->" { if (step != 2) exit 1; step=3; next }
$0 == "<!-- codex-prompt-scope:end -->" { if (step != 3) exit 1; step=4; next }
step == 1 || step == 3 { print }
END { if (step != 4) exit 1 }
' .claude/docs/codex-prompt-guideline.md) || exit 1
codex_prompt_file="$REVIEW_DIR/review-prompt.txt"
{
  cat <<'CODEX_GOAL'
ゴールは {対象ファイル} を {観点} でレビューし、根拠付きの指摘を0〜5件返すこと。
CODEX_GOAL
  printf '\n%s\n\n' "$codex_guard_blocks"
  cat <<'CODEX_TASK'
【対象ファイル】{対象ファイル}
【観点】{観点}
【制約】根拠を優先し、件数を埋めない。ファイルを実際に読み、根拠となる行番号を添える（憶測禁止）。修正は行わない。あなたは起動された視点である。手順素材の『起動方法』節（CLI・MCP の起動）は実行せず、スキル・サブエージェントを起動しない（再委託しない）
【完了条件】各指摘に優先度・行番号・内容を揃える。0件なら「指摘なし」と判断根拠を返す
【出力形式】テーブル
CODEX_TASK
} > "$codex_prompt_file" || exit 1
[ "$(grep -cFx '【モデル運用】' "$codex_prompt_file")" -eq 1 ] &&
[ "$(grep -cFx '【スコープ】' "$codex_prompt_file")" -eq 1 ] &&
! grep -qF '{{CODEX_GUARD_BLOCKS}}' "$codex_prompt_file" || exit 1
grep -nE '^【(モデル運用|スコープ)】$' "$codex_prompt_file" || exit 1
codex exec --ignore-user-config -s read-only -m gpt-6.1-sol -c 'model_reasoning_effort="xhigh"' \
  -o "$REVIEW_DIR/review.md" - < "$codex_prompt_file" > "$REVIEW_DIR/review.log" 2>&1
echo "EXIT=$?"
```

確認対象は正本ファイルだけでなく、**送信する組立済みプロンプト**。`grep` で両見出しが各1件、未展開記号が0件であることを確認してから起動する。`- < "$codex_prompt_file"` が本文をstdinへ渡すため、この方式では `< /dev/null` を重ねない。プロンプトを引数で渡す別の例・ネイティブ差分レビューでは従来どおり `< /dev/null` を使う。`--ignore-user-config` は利用者の config.toml の MCP を外すために付ける（効果・残るもの・制約は [ai-cli-execution/reference.md](../skills/ai-cli-execution/reference.md) §5 Step 2）。追加の配布スクリプトや新しいランタイムは不要。

### Bashを使わない経路（MCP・Read/Grep等）

1. 呼出側が Read 等で本書を読み、4つのマーカーが各1件・記載順どおりにあることを確認する。モデル運用とスコープのマーカー内全文を、マーカー自身を除いて取得する。
2. 各テンプレートの `{{CODEX_GUARD_BLOCKS}}` を取得した全文へ置き換え、**実際に送信する `prompt` 引数**を組み立てる。再記述や要約、受信側への「正本を読め」という指示では代用しない。
3. 送信前に実引数を見直し、ゴールが先頭、両ブロックが各1件・原文一致、未展開記号が0件であることを確認する。許可済みのプロンプト保存先がある場合は Grep でも確認する。Write がない経路ではファイル保存を要求せず、同じ確認を送信文字列に対して行う。
4. 分割した `codex-reply` の各依頼にも同じ展開を行う。CLIの利用可否を確認したうえで経路を選び、モデルとeffortを指定する場合は必ずセットにする。送信前に有料 API への接続確認を行う（[ai-cli-execution/reference.md](../skills/ai-cli-execution/reference.md) §3「有料 API への接続確認」）。

global・リポジトリ入口・実行プロンプトは、セッション開始時のガードをそれぞれの適用層で効かせるために併存する。globalや入口を廃止せず、設計理由と本文の更新先を本書に集約する。

## プロンプトテンプレート

### レビュー依頼用

下記の記号は上記手順で正本全文へ展開してから送信する。件数は上限であり、根拠を優先する。内部構造レビューでは 既存の受入基準 も維持する。

> Codex 自身が**レビュアーとして1回だけ**動く依頼のため、【レビュー粒度】ブロックは入れない。
> Codex に**実装・修正をさせる**場合は次の「汎用（実装・調査依頼用）」を使い、【レビュー粒度】を必ず含める。

```
ゴールは {対象ファイル} を {観点} でレビューし、優先度付きの指摘リストを返すこと。

{{CODEX_GUARD_BLOCKS}}

【対象ファイル】
{ファイルパス（1ファイル）}

【観点】
{1観点（例: セキュリティリスク）}

【制約】
- 指摘は根拠を優先して0〜5件（1〜2件も可）。件数を埋めるために追加せず、根拠となる行番号を必ず添える
- 対象ファイルを実際に読んでから判定する（憶測禁止）
- あなたは起動された視点である。手順素材の『起動方法』節（CLI・MCP の起動）は実行せず、スキル・サブエージェントを起動しない（再委託しない）

【完了条件】
- 各指摘に 優先度（[MUST]/[SHOULD]/[NIT]）・行番号・内容 が揃っている
- 指摘ゼロの場合は「指摘なし」と判断根拠を1行で返す

【出力形式】
| 優先度 | 行番号 | 内容 | のテーブル。テキストで返す（ファイル出力はしない）
```

### 汎用（実装・調査依頼用）

```
ゴールは {達成すべき成果（検証可能な形で）}。

{{CODEX_GUARD_BLOCKS}}

【レビュー粒度】
- 実装 → レビュー → 修正のループは「1ページ / 1機能」単位でのみ回す。ファイル追加・関数追加・小修正のたびに回さない
- レビューは実装単位が動作する状態に達した時点で1回だけ実行する。実装途中の中間状態ではレビューを起動しない
- 指摘は P0（ブロッカー）/ P1（要修正）/ P2（軽微）に分類し、修正するのは P0・P1 のみ。P2 は記録して次の単位へ進む
- 修正後の再確認は修正差分に限定する。単位全体のレビューをやり直さない
- コミットは元ユーザーが明示依頼した場合のみ、その依頼範囲内で行う。この定型ブロック自体を承認とみなさない。依頼がなければ各単位を検証済み・未コミットで完了し、次の単位へ進む

【コンテキスト】
- 対象: {ファイル/ディレクトリ}
- 背景: {エラー内容・関連ドキュメント・経緯}

【制約】
- {従うべき規約・変更禁止事項}

【完了条件】
- {テスト成功・lint 通過など検証可能な条件}

【出力形式】
- {期待する出力形式}。結果はテキストで返す
```
