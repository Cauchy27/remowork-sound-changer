# Codex プロンプト設計ガイドライン

Codex（`codex exec` CLI / `mcp__codex__codex` / `mcp__codex__codex-reply`）へプロンプトを生成する際の共通ルール。
**レビュー依頼・実装依頼・調査依頼など、Codex に指示を出す全ての場面に適用する。**

> どの経路で Codex を呼ぶか（CLI > MCP > Claude 別視点）は [外部AIツール実行ポリシー](ai-cli-execution-policy.md) を参照。本ドキュメントはプロンプトの中身のみを扱う。

> 想定読者: Codex を**呼び出す側**（プロンプトを生成する AI・人間）。Codex 自身が本ドキュメントを読んだ場合は、受け取るプロンプトがこの形式で来ることの説明として扱えばよく、自身の応答形式を変える必要はない。

---

## 🔴 絶対ルール: ゴールを冒頭で明示する

Codex へのプロンプトは、**必ず冒頭に「ゴールは〜」で始まる1文**を置き、達成すべき成果を明確に指示する。

| 原則 | 説明 |
|------|------|
| 成果で書く | 手段ではなく成果を書く。「〜を調べて」ではなく「ゴールは {対象} の {観点} を判定し指摘リストを返すこと」 |
| 検証可能に書く | 判定基準・件数・出力形式を含め、Codex 自身が完了を判断できる形にする |
| 1リクエスト1ゴール | 複数ゴールを1プロンプトに詰めない。分割して順次投入する |

---

## 🔴 絶対ルール: モデル役割分担ブロックを必ず入れる

Codex へのプロンプトには、**下記の【モデル運用】ブロックを原文のまま必ず含める**。ゴール文の直後に置く。

```
【モデル運用】
- あなた（GPT-5.6-Sol）は監督役。自分で実装・調査を抱え込まず、実作業はサブエージェント（GPT-5.6-Luna / reasoning effort: max）へ委託する。**effort は必ず `max` を明示する**（Luna の既定は `medium` のため、無指定では max にならない）
- 大きな問題（設計上の欠陥・原因不明の不具合・広範囲に影響する仕様矛盾）を見つけた時だけ、GPT-5.6-Sol または GPT-5.6-Terra をサブエージェントとして個別に起動し、調査・修正させる
- 上記以外の通常作業で Sol / Terra を起動しない
```

### 理由

| 運用 | 週次レートリミット消費 |
|------|----------------------|
| 全工程を Sol で実行 | 約 **1.5%/1H** |
| Sol 監督 + Luna Max ワーカー | **0.3〜0.7%/1H** |

同一の成果に対して消費が半分以下になる。長時間タスクを現実的な回数こなすための必須運用であり、任意ではない。

### 前提

| 項目 | 内容 |
|------|------|
| 対象モデル識別子 | `gpt-5.6-sol` / `gpt-5.6-luna` / `gpt-5.6-terra` |
| 「Luna Max」の意味 | `gpt-5.6-luna` を reasoning effort `max` で動かす指定（Luna の対応 effort: low / medium / high / xhigh / max） |
| 親セッションのモデル | Sol 固定（`~/.codex/config.toml` の `model = "gpt-5.6-sol"`）。**プロンプト側で親モデルを切り替えない** |
| 専用サブエージェント定義 | **不要**。Codex 側の標準サブエージェント機構をそのまま使う |

> ⚠️ 本ブロックは恒久ルールだが、「その他の注意点」#5（恒久ルールは `AGENTS.md` へ）の例外として**毎回プロンプトに書く**。委託の判断はセッション冒頭で効かせないと Sol が自力実行を始めてしまい、後から是正できないため。

## 🔴 絶対ルール: スコープを固定し過剰処理を防ぐ

Codex はゴールへの執着が強く、放置すると**依頼していない周辺まで直しにいく**。
下記の【スコープ】ブロックを、ゴール文・【モデル運用】に続けて必ず含める。

```
【スコープ】
- ゴールに直接必要な変更だけを行う。ついで修正・周辺リファクタ・体裁調整・命名の統一は行わない
- ゴールの前提に矛盾・欠落を見つけたら、勝手に補完・拡大解釈せず、作業を止めて指摘として返す
- 着手前に次の3点を自己確認する。答えられない項目があれば、実装ではなく質問を返す
  1. 目的: この作業は何のためか。誰の何が変わるか
  2. 代償: この変更で失われるもの・増える運用負荷は何か
  3. 停止条件: どこまでやったら完了か。それ以上やらない線はどこか
```

### 3点の自己確認は本質ギャルレビューの圧縮版

上記3点は `essence-gyaru-review` の7軸（目的 → 意思決定 → 前提 → 因果 → 矛盾 → 業務上の代償 → 次アクション）のうち、
**着手前に効かせないと手遅れになる軸**（目的・代償・次アクション）を Codex 向けに圧縮したもの。

| 使い分け | 手段 |
|---------|------|
| Codex に**着手させる前**の暴走抑止 | 本ブロック（プロンプトへ埋め込む） |
| Codex の**成果物**に対する本質検証 | `essence-gyaru-review` スキルを別途起動する（code-review では Round 1 先頭の横断ゲートとして実行済み） |

**両者は代替関係ではない。** プロンプト側のブロックは「やりすぎを起こさせない」ための事前制御、
ギャルレビューは「出てきたものが目的に適っているか」の事後検証であり、片方では他方を代替できない。

### ゴール文の書き方（過剰処理を防ぐ観点から）

| NG | 理由 | OK |
|----|------|-----|
| 「〜を改善すること」 | 改善の終わりが定義されず、際限なく手を広げる | 「〜の {具体的な指標} を {基準} まで満たすこと」 |
| 「〜を確認し、必要なら修正すること」 | 「必要なら」の判断が Codex に委ねられ、スコープが無限化する | 「〜を確認し、指摘リストを返すこと。修正は行わない」 |
| 「〜をリファクタすること」 | 対象範囲が無い | 「{ファイル} の {関数} を、外部I/Fを変えずに {条件} を満たす形へ書き換えること」 |

## 🔴 絶対ルール: レビュー・修正ループの粒度を固定する

Codex は指示がないと**変更のたび・ファイル追加のたびにレビューを回す**。
1回の追加ごとにレビューが走ると実装が前に進まず、レートリミットだけが消える。
**実装依頼・修正依頼を出す全プロンプトに、下記の【レビュー粒度】ブロックを原文のまま必ず含める。**【スコープ】に続けて置く。

```
【レビュー粒度】
- 実装 → レビュー → 修正のループは「1ページ / 1機能」単位でのみ回す。ファイル追加・関数追加・小修正のたびに回さない
- レビューは実装単位が動作する状態に達した時点で1回だけ実行する。実装途中の中間状態ではレビューを起動しない
- 指摘は P0（ブロッカー）/ P1（要修正）/ P2（軽微）に分類し、修正するのは P0・P1 のみ。P2 は記録して次の単位へ進む
- 修正後の再確認は修正差分に限定する。単位全体のレビューをやり直さない
- 1単位が完成したらコミットし、次の単位へ進む
```

### 粒度の定義（レビュー単位 = 1ページ / 1機能）

| 種別 | 1単位に含めるもの |
|------|-----------------|
| 画面（ページ） | 画面 + API 接続 + その画面の対象テスト |
| 機能（画面をまたぐ） | 機能に属する全画面・全エンドポイント + 対象テスト |
| API 単体（画面なし） | 関連エンドポイント群 + スキーマ/型 + 対象テスト |
| バグ修正 | 該当バグの修正 + 回帰テスト |

### 「タスク分割」との違い（混同禁止）

| 項目 | 何を分割するか | 目的 |
|------|--------------|------|
| タスク分割（下記「その他の注意点」#1） | **1リクエストで投げる依頼の量** | MCP 経路のタイムアウト回避・出力の粒度制御 |
| レビュー粒度（本節） | **ループを回す頻度** | 過剰レビューによる停滞の防止 |

**依頼を細かく分けても、レビューは実装単位ごとに1回。** 分割したリクエストごとにレビューを回さない。

## プロンプト4要素（OpenAI 公式ガイド準拠）

効果的な Codex プロンプトは以下の4要素で構成する。

| # | 要素 | 内容 | 必須度 |
|---|------|------|--------|
| 0 | モデル運用（Model ops） | 監督 = Sol / 実作業 = Luna Max / 大問題時のみ Sol・Terra。上記「絶対ルール」のブロックを原文のまま記載 | 必須 |
| 1 | ゴール（Goal） | 何を達成するか。成果・アウトカムで記述。「改善」「必要なら修正」など終端の無い書き方をしない | 必須 |
| 1.5 | スコープ（Scope） | ゴール外の作業を禁じ、着手前の自己確認3点（目的・代償・停止条件）を課す。上記「絶対ルール」のブロックを原文のまま記載 | 必須 |
| 1.6 | レビュー粒度（Review granularity） | ループを回す単位を「1ページ / 1機能」に固定する。上記「絶対ルール」のブロックを原文のまま記載 | 実装・修正依頼では必須（レビュー専用依頼では不要） |
| 2 | コンテキスト（Context） | 対象ファイルパス・関連ドキュメント・エラー内容・背景 | 必須 |
| 3 | 制約（Constraints） | 従うべき規約・変更禁止事項・レビュー観点・件数上限 | 必要時 |
| 4 | 完了条件（Done when） | 完了と判定できる検証可能な条件（テスト成功・指摘形式充足等） | 必須 |

## その他の注意点（Codex に指示する際の必須チェック）

| # | 注意点 | 理由 |
|---|--------|------|
| 1 | **タスク分割**: 1リクエスト = 1ファイル / 1観点 / 主張3〜5件 | **MCP 経路では必須**（数分でタイムアウトするため分割が根本対処）。CLI 経路では強制ではなく、観点ごとに独立した結論が欲しい場合の任意分割。**分割するのは依頼の量であって、レビューを回す頻度ではない**（上記「レビュー・修正ループの粒度を固定する」参照） |
| 2 | **結果の受け取り方を経路で変える** | MCP はテキストで返させる（タイムアウト時にファイル書き出しも消えるため）。CLI は `-o {ファイル}` で回収し、メインコンテキストへ生ログを流さない |
| 3 | **出力形式を明示する** | テーブル・OK/WARN/NG 等を指定しないと集約コストが跳ね上がる |
| 4 | **憶測回答の禁止を明示する** | 「対象ファイルを実際に読んでから回答すること」を必ず書く |
| 5 | **恒久ルールはプロンプトに詰めない** | 毎回変わらない規約は `AGENTS.md` に置く。プロンプトはタスク固有情報に絞る |
| 6 | **曖昧なタスクは先に計画を出させる** | 実装依頼が曖昧な場合、まず計画のみ返させてから実装を投入する |
| 7 | **検証手順を含める**（実装依頼時） | 再現手順・lint・テスト実行を指示すると出力品質が上がる（公式明記） |

## プロンプトテンプレート

### レビュー依頼用

> Codex 自身が**レビュアーとして1回だけ**動く依頼のため、【レビュー粒度】ブロックは入れない。
> Codex に**実装・修正をさせる**場合は次の「汎用（実装・調査依頼用）」を使い、【レビュー粒度】を必ず含める。

```
ゴールは {対象ファイル} を {観点} でレビューし、優先度付きの指摘リストを返すこと。

【モデル運用】
- あなた（GPT-5.6-Sol）は監督役。自分で実装・調査を抱え込まず、実作業はサブエージェント（GPT-5.6-Luna / reasoning effort: max）へ委託する。**effort は必ず `max` を明示する**（Luna の既定は `medium` のため、無指定では max にならない）

- 上記以外の通常作業で Sol / Terra を起動しない

【スコープ】
- ゴールに直接必要な変更だけを行う。ついで修正・周辺リファクタ・体裁調整・命名の統一は行わない
- ゴールの前提に矛盾・欠落を見つけたら、勝手に補完・拡大解釈せず、作業を止めて指摘として返す
- 着手前に次の3点を自己確認する。答えられない項目があれば、実装ではなく質問を返す
  1. 目的: この作業は何のためか。誰の何が変わるか
  2. 代償: この変更で失われるもの・増える運用負荷は何か
  3. 停止条件: どこまでやったら完了か。それ以上やらない線はどこか

【対象ファイル】
{ファイルパス（1ファイル）}

【観点】
{1観点（例: セキュリティリスク）}

【制約】
- 指摘は3〜5件。根拠となる行番号を必ず添える
- 対象ファイルを実際に読んでから判定する（憶測禁止）

【完了条件】
- 各指摘に 優先度（[MUST]/[SHOULD]/[NIT]）・行番号・内容 が揃っている
- 指摘ゼロの場合は「指摘なし」と判断根拠を1行で返す

【出力形式】
| 優先度 | 行番号 | 内容 | のテーブル。テキストで返す（ファイル出力はしない）
```
