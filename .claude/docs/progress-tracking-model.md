# 進捗トラッキング 3層モデル（正本）

ロードマップ策定から日次報告までを、**3つの層**と**一方向の同期**で構成する。
本ファイルが層構造・ファイルパス・語彙の正本であり、関連スキルはここを参照する。

## なぜ3層か

進捗情報を1ファイルに集約すると、粒度の異なる情報（四半期テーマ / 日付 / 実装タスク）が混在して更新が破綻する。
逆に無定義のまま複数ファイルへ書くと、どれが正かわからなくなる。
そこで**層ごとに問いを1つだけ持たせ**、層をまたぐ複製を禁止する。

## 層の定義

| 層 | 答える問い | 正本ファイル | 粒度 | 主担当スキル |
|----|-----------|------------|------|------------|
| L1 戦略層 | 何を・なぜ・どの順で作るか | `.claude/roadmap.md` | 四半期 × テーマ | roadmap-planning |
| L2 時間層 | いつまでに終わらせるか | `.claude/schedule.md` | 日付付きマイルストーン / 週次タスク | schedule-management |
| L3 実行層 | 誰がどう進めるか | チケット（下記「実行層の所在」） | チケット / 仕様単位 | ticket-creation, spec-planning, sprint-planning |

この表が層定義の正本。他ドキュメント（`skill-reference.md` 等）に定義そのものを複製しない。要約する場合も本ファイルへのリンクを添える。

### 実行層の所在

配布先リポジトリによって実行層の置き場所が異なる。**優先順位は以下**:

1. `../taskhub/teams/{TEAM}/{REPO}/tickets/` — taskhub を運用しているリポジトリはこれが正
2. `.docs/ticket/` — taskhub 未導入時のフォールバック（レガシー互換）
3. `.docs/spec/`（`go/` `next/` 配下含む） — 仕様書内の実装チェックリスト。チケットの**下位**であり、単独の進捗ソースにしない

## 書き込み主体

各正本ファイルへの書き込み主体は1スキルに限定する。他スキルは「引き渡す（下り）」「報告する（上り）」までで、他層のファイルを直接編集しない。

| ファイル | 書き込み主体 | 他スキルの関与 |
|---|---|---|
| `.claude/roadmap.md` | roadmap-planning のみ | schedule-management は引き渡しを受けるだけで直接編集しない |
| `.claude/schedule.md` | schedule-management のみ | roadmap-planning（下り）・ticket-creation 等（上り）は直接編集しない |
| L3 チケット | ticket-creation のみ | spec-planning / sprint-planning はチケット起票を ticket-creation に委ねる |

「引き渡す」「報告する」の実体は、**同一セッションで続けて相手スキルの SKILL.md を読み、その手順を実行する**ことを指す。自スキルが相手ファイルを Edit で直接書き換えてはならない。
Cursor / Codex 等、スキルが自動連鎖しない環境では、この受け渡しを手動で行う必要がある（相手の SKILL.md を明示的に開いて手順に従う）。

## 同期の方向

```
L1 roadmap.md  ──展開──▶  L2 schedule.md  ──展開──▶  L3 チケット
      ▲                        │    ▲                       │
      └──状態ロールアップ────────┘    └──状態ロールアップ───────┘
```

### 下り（展開）: 必須・手順化されている

- **L1 → L2**: 四半期テーマの中で日付が確定した節目を、`schedule.md` の「マイルストーン」表へ1行として起こす。roadmap-planning Phase 6 が担当。
- **L2 → L3**: マイルストーン配下の作業をチケットへ分解する。sprint-planning / ticket-creation / spec-planning が担当。

### 上り（ロールアップ）: 状態遷移のみ

上りで伝えるのは **完了 / 遅延 / ブロック** の3種の状態遷移。内容（タスク名・実装詳細）は複製せず、**状態と理由を1行**だけ伝える。

- **完了**: 下層が完了した時点で上層の該当項目を「完了」にする（判定手順は次項「完了判定」）。
- **遅延 / ブロック**: 完了を待たない。下層で期限に間に合わないと判明した時点で、直ちに「〇〇のため遅延見込み」のように状態と理由を1行添えて上層へ伝える。

#### 完了判定（L3 → L2）

1. L2 `schedule.md` のマイルストーン表にある「実行チケット」列で、対象マイルストーンに紐づくチケット ID / パスを確認する。
2. L3 側の各チケットの「マイルストーン（L2）」欄が同じマイルストーン名を指しているものを grep 等で列挙する。
3. 列挙した全チケットの「状態」フィールドが「完了」であることを確認する。1件でも未完了ならそのマイルストーンは未完了のまま。
4. 全て「完了」であれば、L2 の該当マイルストーンを「完了」にする。

この判定はチケット側に「状態」フィールドが存在することが前提。フィールドの追加・運用は ticket-creation 側の担当とする。

#### 完了判定（L2 → L1）

L2 のマイルストーンが全て「完了」になった時点で、L1 の該当テーマに完了印を付ける。

### 禁止事項

- 上層に下層の詳細を書き写す（例: `schedule.md` に個別チケットのタスク名を列挙する）
- 同じ情報を2層で編集可能な状態にする（書き込み主体は前掲「書き込み主体」節のとおり1スキルに限定する）
- L3 を経由せず L2 に実装タスクを直接足す（週次タスク欄は「その週限りの雑務」に限る）

## 語彙の分離（誤発動防止）

「マイルストーン」は L2 の専用語。L1 では使わない。

| 概念 | L1 での呼称 | L2 での呼称 |
|------|-----------|-----------|
| 期間のまとまり | テーマ / 四半期ゴール | （持たない） |
| 日付が確定した節目 | （持たない） | マイルストーン |
| 個々の作業 | ロードマップアイテム | 週次タスク（雑務のみ） |

スキルの `description` に書く発動キーワードもこれに従う。
「マイルストーン」を含む依頼は schedule-management が受ける。四半期の中身を組み替える依頼は roadmap-planning が受ける。

## 境界ケース

どの層にも明確に属さない情報の扱いを定義する。

- **四半期をまたぐ長期テーマ**: L1 では複数四半期にわたり同一テーマ名で継続表記する。L2 側は四半期ごとに別マイルストーンとして切り、四半期をまたいで同一マイルストーンを引きずらない。
- **緊急割り込み・インシデント対応**: L3 チケットとして起票する。L2 には、期限に影響する場合のみマイルストーンの「遅延」として反映する。インシデント対応そのものの手順は `.claude/skills/incident-response/SKILL.md` の担当であり、本モデルは進捗の記録先だけを定める。
- **L3 を経ない軽微な修正（typo 等）**: どの層にも記録しない。git log のみで足りる。

## 報告系スキルのデータソース

報告スキルは**自分で進捗を数えず、上記の正本ファイルを読む**。

| スキル | 読む層 | 補助ソース |
|-------|-------|----------|
| standup（日次） | L2 週次タスク | git log / gh pr |
| status-report（週次・月次） | L2 マイルストーン + L3 チケット | git log |
| stakeholder-update（経営向け） | L1 テーマ + L2 マイルストーン | metrics-review 出力 |
| metrics-review | （進捗層は読まない。KPI が対象） | — |

正本ファイルが未整備のリポジトリでは、報告スキルは「L2 未整備につき git log ベースで代替」と明記したうえで生成する。**黙って代替しない。**

## 初期セットアップ

L1 / L2 のファイルは初回に生成が必要。

- `.claude/schedule.md`: schedule-management スキルが不在を検出したらテンプレートから生成する
- `.claude/roadmap.md`: roadmap-planning スキルの Phase 5 で初回生成する

どちらも**未作成のまま放置しない**。存在しない場合は「未整備」と報告する。
