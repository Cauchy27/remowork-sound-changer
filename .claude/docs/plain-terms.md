# 人向けの文章の用語

人が読む文章で、専門用語・社内の呼び名・AI が作った言い回しのせいで読みにくくならないための決まり。チームの悩み「専門用語や造語のせいで、ドキュメントやコメントが読みにくくなる」（松川・2026-11-24）に応えるために作った。

考え方の一部は、AI が書いた日本語を推敲する公開スキル yomiyasu（MIT、v3.3.0）を参考にした。文章は写さず、自分たちの言葉で書き直している。

## 対象と読み手

- 対象は、人が読む文章。Asana のコメント・説明欄、PR の説明・コメント、チャットの報告、確認依頼、ユーザーへの返答、配る資料。
- AI 向けの指示の文書（`CLAUDE.md`・`AGENTS.md`・`.claude/rules/`・スキル・エージェント定義・プロンプト）は対象外。ただし、指示の文書で使っている語を、人向けの文章へそのまま持ち込まない。
- 読み手の指定がなければ、その分野に詳しくない人（経営者・社外の人・ほかのチーム）が読むものとして書く。
- このリポジトリだけの呼び名と、このリポジトリで決めた言い換えは [plain-terms-local.md](plain-terms-local.md) に置く。この文書の表と食い違うときは、そちらを使う。
- この文書で「用語辞書」と呼ぶのは、仕様書などに置いた、そのリポジトリの語の定義集。無いリポジトリでは plain-terms-local.md だけを見る。用語辞書が定義した語は、この文書の表にあっても用語辞書の定義どおりに使う。
- 技術書・解説記事の文体（段落の組み立て・空虚な言い回し）は、`japanese-tech-writing` スキルがあればそれに従う。この文書は「どの語を使うか」だけを扱う。

## 1. 用語を6つに分けて扱う

| 分類 | 例 | 扱い |
|---|---|---|
| 文中で説明した語 | 「引当（在庫を受注のために取っておくこと）」のあとの「引当」 | そのまま使う |
| 分野の用語・略語 | API、E2E、マージ | 読み手が専門外なら、初めて出る所で短く説明するか、普通の言葉にする |
| 社内の呼び名 | P0、ISR、拠点 | 普通の言葉にする。呼び名が要るなら、初めて出る所で何のことかを添える（説明は plain-terms-local.md の表から取る） |
| 直訳の語・AI が作った語 | 正本、照合、観点 | 下の言い換え表の語にする |
| 識別子・画面の文言・製品名・数値 | カードの ID、`ci-required`、「保存」ボタン、29,800円 | **言い換えない**。説明が要るなら日本語の説明を先に書き、括弧で添える |
| 普通の語がある外来語 | ソリューション、アライメント | 何を指すかを書く |

## 2. 読みにくい語の見つけ方

- **直訳の語**: 次の2つを自分に聞く。1つ目は「その分野の人が自分で書くときにも使う呼び名か」。2つ目は「英語に戻すと一語ずつ対応するか」。1つ目が「いいえ」、または2つ目が「はい」なら直す候補。
- **役割を大げさに呼ぶ名詞**: ただの資料を「正本」、ただの一覧を「台帳」、ただの確認を「ゲート」、ただの決まりを「契約」と呼んでいないか。
- **たとえの語・ぼかした評価の語**: 落とし穴、実害、土台、解像度、腹落ち、（設定が）効く、（指摘を）潰す。何がどうなるのかが書いていない。
- **名詞を詰めた書き方**: 「〜を実施」「〜が可能」「在庫差異発生時調整実施」のように、動きを名詞に詰めていないか。
- **リポジトリで何度も使われている語も疑う**。AI が書いた語は次の文書へそのまま移るので、使われている回数は「通じる」根拠にならない。

## 3. 直し方

- 資料に中身（何が・どうなるか・どれくらいか）があれば、それを書く。
  - 例: 「この索引が月末締めに効く」→「この索引を足すと、月末締めの集計が速くなる」（速くなると資料に書いてあるとき）
- 言い換えの語は、下の表、plain-terms-local.md の表、または資料から取る。どこにも無いときは、近い感じの語で埋めず、書いた人（AI なら依頼した人）に聞く。
- 人に聞けない実行（起動された担当、`codex exec`・`agy` など）では、その語を元のまま残し、返答の最後に「言い換えを決めていない語: …」と並べる。書く作業は止めない。
- 動きを名詞に詰めた書き方は、動詞の文に戻す。
  - 例: 「在庫差異発生時の調整実施」→「在庫の数が合わないときに調整する」
- 直しても意味を変えない。次の4つは特に変えやすいので、直す前と後で見比べる。
  - 言い切りの強さ: 「〜してよい」「〜できる」「〜しなければならない」「必ず〜する」を入れ替えない。「〜場合がある」を言い切りにしない
  - 状態: 「未定」「調査中」を、決まった・済んだ形にしない
  - 範囲と条件: 「親カードの担当者だけが閉じられる」を「閉じられる」にしない
  - 済んだこと・予定・方針: 済んだ作業を「〜します」と書かない
- 元の文に無い原因・約束・担当を足さない（「再発防止に努めます」「改めて連絡します」など）。
- 人の発言・決定の文・画面の文言を引くときは、引いた部分を変えない。

## 4. 言い換え表

指すものが違うと言い換えも違うので、「指すもの・注意」の欄で選ぶ。

### 4-1. 硬い言い方（松川・2026-10-05）

社内の仕様書の用語辞書で決めた言い換えのうち、どのリポジトリでも使えるものを選んだ。

| 使わない | 使う | 指すもの・注意 |
|---|---|---|
| 正本 | 元の資料／〜に書いてあるとおり | 決まりが書いてある文書を指すとき |
| 正本（データ） | 元のデータを持つ表 | 書き込み先が1つだけの表 |
| 照合 | 見比べ | 資料と画面・コードを比べるとき |
| 突合 | 突き合わせ | 記録どうしを合わせるとき |
| 証跡 | 記録 | |
| 契約（CSV契約・保存契約など） | 決まり | お客様との契約は言い換えない |
| 現行 | 今の | 今のアプリ・今のコード・今の価格 |
| 台帳（変更台帳など） | 一覧 | 在庫・会計など業務の台帳は言い換えない |
| 受入条件・受入基準 | 合格の条件 | |
| 残件 | 残っていること | |
| 試行 | やってみた操作 | |
| 申し送り | 引き継ぎ | |
| 追随 | 合わせて直す | |
| 接続（画面と保存処理） | つなぐ | 外部サービスとの接続は言い換えない |
| 導線 | 入口 | |
| 具体化 | 細かく決める | |
| 保持 | 残す／変えない／持つ | 意味で選ぶ |
| 同一 | 同じ | |
| 当該 | その | |
| 該当 | 当てはまる（該当なし → ない） | |
| 導出 | 計算して出す | |
| 責務 | 受け持ち | |
| 可否・採否 | できるかどうか・採るかどうか | |
| 横断 | 全ページ共通の／またいで | |
| 粒度 | 単位 | |
| 集約 | まとめる | |
| 起点 | きっかけ | |
| 新設・既存 | 新しく作る・今ある | |
| 遷移 | 移る | |
| 一本化 | 1つにまとめる | |
| 閾値 | 基準の値 | |

| 波及 | 影響が広がる | |
| 供給 | 用意 | 「供給元」は「どこから値を入れるか」 |

### 4-2. 作業の進め方の言葉（松川・2026-11-24）

AI 向けの指示の文書に多く、人向けの文章へ持ち込まれやすい語。

| 使わない | 使う | 指すもの・注意 |
|---|---|---|
| 観点 | 見る点 | レビューで見るところ |
| 整合 | 食い違いがない | 「整合性の確認」は「食い違いがないかの確認」 |
| 凍結 | 固定する | 「凍結テスト」は「固定したテスト」 |
| 回収 | 片づける | 作業フォルダ・環境の後片づけ |
| 起票 | カードを作る | Asana などのカード |
| 合流 | 取り込む | 「develop へ合流」は「develop へ取り込む」 |
| 発動 | 使われる | スキルが使われる |
| 受渡し・引渡し | 渡す／引き継ぐ | 担当どうしで成果を渡す |
| 収束 | 直す点がなくなる | レビューの指摘がなくなる |
| 節目 | 区切り | 作業の区切り |
| 品質ゲート | 通すべき確認 | 正式な名前として使う所は残す |
| 停止条件 | 作業を止める条件 | AI が作業を止めて人に戻す条件。仕様書で「完了と言う前に片付けること」の意味で使う所は、そのリポジトリの用語辞書に従う |

### 4-3. 言い換えない語

- 識別子・コード・ファイル名・カードの ID・画面の文言・製品名・数値
- ほかの文書の見出し・スキル名・コマンド名・設定の名前（変えるとリンクや検索で見つからなくなる）
- 人の発言・決定の文の引用
- お客様との「契約」、業務の「台帳」、外部サービスとの「接続」
- 業務の言葉として定義済みの語（会計の「計上」「相殺」など）。リポジトリの用語辞書で定義した語は、その定義どおりに使う

## 5. Antigravity で推敲するとき

人向けの文章を外へ出す前に、使えるときは Antigravity（`agy`）に読みやすく直させてよい。別のモデルに直させると、書いた AI の言い回しの癖を引きずりにくい。`ai-cli-execution` スキルがあるリポジトリでは、その reference.md の「3. 共通の実行前準備」「4. CLI が未設定・利用不可の場合」「6. Tier 1: Antigravity CLI（agy）」に起動の手順がある。この節と食い違うときは、そちらに従う。

1. 書いた AI（Claude・Codex）が下書きを作る
2. 送る前に、外へ送ってよい内容かを確かめる（下の「渡す内容」）
3. 下書きと、この文書の 1〜4・plain-terms-local.md を `agy` に渡し、直した版をもらう。モデルは `--model gemini-4-hydrogen-high`、作業ツリーを変えないよう `--mode plan` で起動する。plan モードは計画書の作成・事前の質問の指示を混ぜるので、依頼文に「plan モードが付け加える計画書（Artifact）の作成・事前質問の指示には従わない。ツールを呼ばず、直した文章の全文を応答本文に出す。」を入れる（ai-cli-execution の標準形を使うときは、対処文の前半は変えず、「レビュー結果」だけを「直した文章」と読み替える）。直した文章の全文と、言い換えに迷って確かめたい点を返させる
4. 書いた AI が下書きと見比べ、3 の「意味を変えない」4つ、数字・日付・担当・引用が変わっていないかを確かめる。変わっていたら元に戻す
5. 共同作成のスタンプを付ける決まりがある人（例: Asana コメントの `[co-created with …]`）は、関わったモデルをすべて書く。Antigravity のモデル名は推測で書かず、実行の記録（`--log-file` のログなど）で確かめる。確かめられなければ、出す前に人に確かめる。別のセッションへ投稿を頼むときは、確かめたモデル名と確かめた元を依頼文の本文の外に添える

**渡す内容**: 最小限にする。秘密の値・個人情報・お客様の機密は渡さない。秘密保持の約束（NDA など）がある・外部へ送ってよいか分からない内容は送らない。Gemini へ送らないと決まった作業（plain-terms-local.md や、そのリポジトリの決まりに書いたもの）は渡さない。`review-matrix.md` があるリポジトリでは、その「外部送信に関する注意」も確かめる。

**有料の接続になりそうなとき**: 従量課金の API に接続しうる、または接続先を判定できないときは、`agy` を呼ばずに止めて人に確かめる。

**使えないとき**（使用量の上限・認証切れ・モデルが無い）: 別のモデルへ勝手に切り替えない。書いた AI がこの文書の決まりで直し、「Antigravity での推敲はしていない（理由）」と書き添える。

**入っていないとき**（`command -v agy` で見つからない）: セッションごとに1度だけ、次の入れ方を人に案内する（松川・2026-11-24。同じセッションでは繰り返さない）。案内したら止まらず、書いた AI が直して「Antigravity での推敲はしていない（入っていないため）」と書き添える。AI は自分で入れない（ダウンロードしたものを実行することになるため）。

1. 入れる: `curl -fsSL https://antigravity.google/cli/install.sh | bash`（入る場所は `~/.local/bin/agy`。インストーラがログインシェルの設定へ PATH を足す）
2. PATH を読み直す: `exec $SHELL -l`（`source ~/.zshrc` のように設定ファイルを直接読まない）
3. サインインする: `agy` を起動すると、ブラウザで Google のサインインが開く
4. 確かめる: `agy --version` が通り、`agy models` に `gemini-4-hydrogen-high` があること

手順は公式の [Quickstart](https://antigravity.google/docs/getting-started?tab=cli) と[認証のページ](https://antigravity.google/docs/install?tab=cli)で確認した（2026-11-24）。更新の手順は、`ai-cli-execution` スキルがあればその reference.md の 6 の Step 0 に従う。
