# コンテキスト管理（Prompt is too long 対策）

サブエージェント並列実行時のコンテキスト爆発を防ぐルール。

## サブエージェントの出力ルール

大量の結果は呼出側が指定した**許可済みの保存先**へ出力し、メインには結論・根拠・残課題の要約（目安3〜5行）と保存先を返す。Write が使えない、または保存先が許可されていない場合は、要約を戻り値で回収する。保存のためだけに権限を広げない。短い結果は戻り値だけでよい。

CLI の `-o` や呼出側のリダイレクトによる回収も利用できる。レビュー対象は編集せず、指定された成果物だけに書き込む。

### 一時ファイルパターン

```
.tmp/{task_name}/           # タスク実行ごとに作成
├── step1_agent_a.md        # Step 1 の結果
├── step1_agent_b.md
├── step2_review.md         # Step 2 の結果
└── step3_advice.md         # Step 3 の結果
```

### サブエージェント呼び出しテンプレート

```
Task(subagent_type="{agent_type}", prompt="
以下のファイルを自分でReadして、{タスク内容}を実行してください。

入力ファイル（自分でReadすること）:
* {入力ファイル1}
* {入力ファイル2}

【出力ルール】
大量の結果は、書込手段と保存先が許可されている場合だけ {出力ファイルパス} へ保存してください。
書込不可なら結論・根拠・残課題を要約して戻り値で返してください。保存だけのために権限を広げないでください。
このメッセージへの返答は3〜5行の要約と、保存した場合はそのパスにしてください。
")
```

## リーダーのコンテキスト節約ルール

| やること | やらないこと |
|----------|-------------|
| サマリーファイルがあればそれを読む | 元データの全文を読む |
| 大きなファイルはoffset/limitで部分読み | ファイル全体を一度に読む |
| リファレンスは使うステップでのみ読む | 最初にすべて読み込む |
| 保存できた大量結果は必要部分だけ読み、書込不可なら戻り値の要約を回収 | 大量結果をコンテキストに全展開 |

## 適用基準

| シナリオ | 対策 |
|----------|------|
| 複数サブエージェントから大量結果を回収 | 許可済み保存先へ出力。Write不可なら戻り値を要約に限定 |
| 入力データが1000行超 | サマリーファイル作成 or offset/limit |
| 複数フェーズのパイプライン | 各フェーズでリファレンスを遅延読み込み |
| 前回の出力を参照する | 結論部分のみoffset読み |

## クリーンアップ

タスク完了時に `.tmp/` ディレクトリを削除する。

```bash
rm -rf .tmp/{task_name}/
```

## 配置ポリシー（何をどこに置くか）

判断基準は1つ。**「このルールは毎ターン読む必要があるか？」→ No なら `docs/` か `skills/` に置く。**

`.claude/rules/` は CLAUDE.md と同様に毎ターン自動読み込みされる。**安易な追加は禁止**（追加には正当な理由が必要）。

| 配置先 | 用途 | 読み込み | 追加基準 |
|--------|------|---------|---------|
| `CLAUDE.md` | 核心ルール・プロジェクト概要 | 毎ターン自動 | 全作業で必要なもののみ |
| `.claude/rules/` | 全作業に適用される行動ルール | 毎ターン自動 | **追加には正当な理由が必要** |
| `.claude/docs/` | リファレンス・テーブル（OKF bundle） | 必要時にRead | 参照頻度が低いもの |
| `.claude/skills/` | **業務フロー**・繰り返し手順・スキル固有のルール | スキル発動時 | スキル内で完結するもの |
| `.docs/` | **git管理対象の成果物**（OKF bundle: 仕様書・チケット・レポート・ログ等） | 必要時にRead | チームで共有・参照するドキュメント |
| `MEMORY.md` | 直近の意思決定・ユーザー訂正・引き継ぎ情報 | 毎ターン自動（グローバル領域、コンテキスト消費対象） | 次セッションで必要な短期記憶。業務フロー化したら skills へ。実体はリポジトリ外の `~/.claude/projects/<project>/memory/MEMORY.md`（ユーザーのグローバル自動メモリ） |

### 知識の置き場（3 条件）

知識をどこに置くかは、使う側の数と中身の性質で決める。ファイルの長さだけで配置を決めない。

1. 1 つのスキルだけが使う補足 → そのスキルの `reference.md`（または `.claude/skills/<スキル名>/` 配下）
2. 2 つ以上のスキルが参照する、または人も読む共通知識 → `.claude/docs/`（当面は直下に置き、領域別のサブディレクトリは作らない）
3. 手順・停止条件・成果物を持たない純知識 → スキル（SKILL.md）にしない。1 か 2 の置き場へ置く

3 はスキル一覧の本数を増やさないための条件である。一覧の description はモデルのコンテキスト窓の 1% を予算とし、超えると呼び出し頻度の低いスキルから落ちる。手順を持たない知識をスキルにすると、発動させたいスキルの description を押し出す。置き場所を `.claude/docs/` と `reference.md` の間で動かしても一覧の予算は変わらない（どちらも必要時に Read する）。

### メモリ vs スキル 判断フロー

- 「次セッションでも参照するか？」→ Yes → `MEMORY.md`
- 「同じ手順を何度も踏むか？」→ Yes → `.claude/skills/`（スキル化）
- どちらでもない → 記録しない

### 記憶方式 vs 長文脈直接投入の使い分け（損益分岐の目安・中期検討事項）

Beyond the Context Window（arXiv:2603.04814）の実験知見によれば、精度は長文脈への直接投入が
最大35pt優位、コストの損益分岐は概ね10ターン、20ターン地点では記憶方式（分割・ポインタ経由）が
約26%安価という結果が報告されている。これを踏まえた目安:

| セッション長の見込み | 推奨 | 理由 |
|---|---|---|
| 短セッション（10ターン未満想定。単発の事実確認・軽微修正等） | 新規メモリはMEMORY.md本体に直接厚く書き、個別ファイルへの分割・ポインタ化は避ける | 精度面で長文脈直接投入が有利。分割のオーバーヘッドがコストメリットに転じる前にセッションが終わる |
| 長セッション（20ターン超想定。template-rollout・comprehensive-testing等の横展開/網羅系） | 現行の「1行ポインタ＋個別ファイル」方式を維持 | 20ターン時点で記憶方式が約26%安価。ターン数が伸びるほど差が拡大する |
| 10〜20ターンの中間帯 | セッション長だけを理由に判断を変えない。既存の「メモリ vs スキル 判断フロー」を優先 | 損益分岐点付近であり精度・コストの優劣が実測なしに逆転する保証がない |

**実測方法**: Stats パネルのキャッシュ内訳から、ヒット率 = `cache_read / (cache_read + input)` を
算出する（v2.1.221以降でキャッシュ内訳表示に対応）。この値が低い状態が続くリポジトリは、
毎ターンMEMORY.md本体とポインタ先ファイルを往復して読み直している＝実態は短セッション寄りの
利用である可能性が高く、細分化方針を見直す材料にする。

**注記**: 上記は論文実験（一般的なQAタスク設定）に基づく目安であり、本リポジトリでの実測値では
ない。恒久ルール化はせず中期検討事項として据え置き、Statsパネルでの実測が蓄積した時点で
再評価する。
