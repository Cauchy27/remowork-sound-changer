# レビュー視点・観点マトリクス（正本）

**本ファイルは全レビュースキルの共通正本である。** 視点・観点・裁定ルールをここでのみ定義し、各スキルは参照する。各スキルで視点定義を再掲・改変してはならない（二重管理になる）。

共通前提は、コード・文書・エージェント・デザイン・業務評価のレビュースキルに適用する。3視点の実行モデルに接続している主なスキルは `code-review` / `internal-structure-review`。`agent-review` 等は共通前提を参照するが、各スキル固有の実行構成を維持する。`design-critique` も共通前提のみを適用し、単独実行を維持する（判断理由は「design-critique が単独実行のままである理由」節を参照）。

---

## 全レビュースキル共通の前提

**AIの出力は「仕様を曲解しがちなジュニアのPR」として扱う。** 実装だけでなく、レビュー指摘・テスト・仕様解釈も未検証の候補である。別モデルの賛同、指摘0件、AIによるファクトチェックのPASSだけで正しさを確定しない。

**レビューするAIやテストを作るAIも仕様を曲解し得る。** 「AIが仕様を正しく理解した」は検証の前提に置かない。実装・レビュー指摘・テストの期待値をそれぞれ正本へ照合し、AI同士で一致していてもこの照合を省かない。

**委託時もこの前提を引き継ぐ。** 呼出元は「AIの出力は『仕様を曲解しがちなジュニアのPR』として扱う」を委託先のプロンプトへ明記し、対象版・参照する正本・不変条件/受入条件・未確認事項・許可範囲を渡す。送信前に実際の本文へ入っていることを確認する。委託先がファイルを読めない経路では、必要な正本内容も埋め込む。

### 役割と根拠

| 担当 | 役割 | 判定の根拠 |
|---|---|---|
| AIレビュアー | 仕様の曲解、セキュリティ欠陥、エッジケース、不変条件を破る反例を探す | 正本仕様・実物・再現条件。実装者の説明や他AIの結論だけでは採用しない |
| 機械検証 | 型・静的解析・境界値/異常系/回帰テスト等で、明示した条件を満たさない候補を足切りする | 対象版に対する実コマンドと結果。PASSは検査した条件の範囲に限る |
| 人間 | 業務上の不変条件、仕様解釈、許容する代償を最終レビューし、承認・マージを判断する | 正本との対応、反例と検証結果、未確認事項。AIのPASSを人間の承認へ読み替えない |

### コード変更の標準フロー

1. **正本と不変条件を固定する**: 対象版、仕様・決定記録、受入条件、常に守る業務ルールを特定する。期待値は正本から導き、実装を見て都合よく決めない。結果を左右する未決事項は人間へ戻し、依存する工程だけ保留する。
2. **実装単位を完成させる**: 「1ページ / 1機能」を動く状態まで作る。軽量な型チェックやlintは先に実行してよい。レビュー粒度・修正対象・再確認範囲は impl-review-loop を正本とする。
3. **別モデルで独立に反例を探す**: 正本と対象を共通入力とし、初回は他レビュアーの結論を見せない。独立レビュー後に不一致を突き合わせる。コードではセキュリティとエッジケースも複数視点が重複して確認し、実コード・一次情報で指摘を検証する。モデル/経路の不足・未確認は記録し、別モデルで実施したことにしない。
4. **反例を検証へ落とす**: 妥当な不具合は修正し、破られた不変条件を境界値・異常系・回帰テストで検証する。競合・順序・再送が関係する場合はその条件も含める。テストは仕様を検証し、AI実装の挙動をそのまま期待値にしない。テストの無効化や期待値の緩和で通過させない。
5. **機械的に足切りする**: 対象に関係する型チェック・静的解析・テスト・ビルドと既存CIの必須項目を実行し、対象版と結果を記録する。必須検証のFAIL・未実施は人間レビューへ進める準備完了としない。CIが存在しない場合はその事実を記し、ローカル検証をCI成功と呼ばない。
6. **人間が最終レビューする**: 不変条件自体が業務上正しいか、仕様の曲解や未検査の破綻が残っていないかを確認する。承認・マージは人間が判断する。AIの作業完了、人間の承認、マージ、公開は別の状態として報告する。

レビュー専用の依頼では、修正・テスト追加・コミット・外部送信の権限をこのフローから増やさない。反例と必要な検証を返し、未実施の工程を明記する。修正後の再確認は差分と影響する検証に限定する。

### コード以外への適用

文書・スキル・デザイン・広告/指標・請求書/ベンダー評価では、型チェックやコードCIを一律に要求しない。正本資料、決定済み条件、数値定義等を基準に、リンク・構造・算術・集計等の適用可能な機械検証と一次情報照合を使う。実行手段がなければ未確認として返す。各スキルの単独/並列構成や権限を、この共通前提だけで変更しない。独立性と実施範囲を申告し、AI評価を人間の業務判断・公開・支払い等の承認へ読み替えない。

### 網羅レビューの回数上限

**同じ対象への網羅レビューは3回まで。4回目以降は差分レビューだけを行う。**

- **1回の数え方**: そのスキルのレビュー手順を対象全体に通しで1回実行したもの（例: `code-review` の Round 1〜4、`internal-structure-review` の Step 1〜4）。視点の縮退で一部の視点だけを再実行した場合、その再実行は数えない。
- **差分レビューの範囲**: 直前のレビュー以降に変更した箇所に加え、その影響範囲（変更箇所を参照・呼び出している箇所、同じ不変条件・受入条件を担う箇所）。変更行だけに絞らない（修正起因の回帰を見落とすため）。
- **より厳しい規定を優先（回数）**: スキルがこれより少ない回数を定めている場合、回数はそちらに従う。`impl-review-loop` と、実装の途中で呼ばれた `code-review` は、網羅レビューを単位ごとに初回1回とし、以降は差分レビューだけを行う（現行どおり）。差分レビューの範囲は、スキルを問わず上記「差分レビューの範囲」に従う。
- **上限を超えて網羅レビューを行ってよい場合**（本節の3回、またはスキルが定めるより少ない回数を超える場合）: 人間が明示的に指示した場合／正本仕様・不変条件・レビュー対象の範囲が変わった場合（別の対象として回数を数え直す）。この2つに限る。
- **差分レビューの停止条件**: `impl-review-loop` ルール5のうち「直近2周で新規指摘件数が減少していない」「同一指摘への修正が2回失敗している」に該当したら、差分レビューを続けずエスカレーションする。
- **記録**: 出力フォーマットの「周回」欄に「網羅 n/3・差分 k 回目」（k は直近の網羅レビュー以降の差分レビューの回数）と、差分レビューで見た範囲を残す。
- **適用範囲**: 共通前提を適用する全レビュースキル。PR・リリース前などレビュー自体が目的の呼び出しにも適用する。

### 人間へ渡す検証記録

各スキルの既存出力に、対象版、参照した正本、不変条件/受入条件、検証した反例、実行した機械検証と結果、未確認事項、人間の判断待ちを含める。コードでは不変条件と対象テストの対応も示す。記録がない工程を実施済みにしない。

例: 「同じ決済要求を再送しても請求は1回」「他の利用者の注文を操作できない」「取消済み注文は出荷へ遷移しない」。型が合っていることや正常系テストのPASSだけでは、これらを保証できない。

参考: [OWASP Business Logic Security](https://cheatsheetseries.owasp.org/cheatsheets/Business_Logic_Security_Cheat_Sheet.html) は業務の不変条件を記述し、実装ではなく業務ルール、競合、操作順序をテストするよう勧めている。ここで定めるAI・機械・人間の役割分担は本リポジトリの運用方針である。

## 用語（最初に読むこと）

過去、`code-review` の「13視点」と `internal-structure-review` の「3視点」が**同じ語で別物**を指し、統合を妨げていた。本正本では次のとおり分離する。

| 層 | 語 | 意味 | 定義場所 |
|---|---|---|---|
| 第1層 | **視点** | **誰が見るか**（レビュアーの立場・使用モデル） | 本ファイル |
| 第2層 | **観点** | **何を見るか**（評価軸） | 本ファイル |
| 第3層 | **チェックリスト** | **どう見るか**（対象別の具体項目） | 各スキル |
| 軸の外 | **粒度** | **どの単位で回すか**（1ページ / 1機能）。視点・観点・チェックリストのどれとも直交する運用条件で、本正本では定義しない | `impl-review-loop` スキルの「レビュー粒度」セクション |

「13視点」のような**観点細目を視点と呼ばない**。

## 第1層: 視点（誰が見るか）

3視点。それぞれ**実CLIで独立プロセスとして実行する**ことを原則とする。

| 視点 | 実行コマンド | 性格・強み | 主担当の観点 |
|------|------------|-----------|------------|
| **Claude Code** | `claude -p` | 全体把握・全体設計・アーキテクチャ・セキュリティ | アーキテクチャ・構造 / セキュリティ / 経営・事業 |
| **Codex** | `codex` | 粘り強さ・ゴール要件への執念。「終わったつもり」の検出 | 要件充足 / 実装品質・エッジケース / 規約・コンプライアンス |
| **Antigravity** | `agy` | グラフィック・空間把握・視覚的情報設計 | UX・体験 / ドキュメント・自己文書化 |

### 視点を実CLIで実行する理由

**同一セッション内のペルソナは自己レビューになる。** 自分が書いたものを、自分の文脈を共有する役が見ても、前提ごと見落とす。

実測例（2026-08-16）: あるワークフローの相対リンクについて、同一セッション文脈の Claude Code 役は「破損ゼロ」と判定し、別前提で検証した役が「配布後に約20箇所が全滅」を発見した。前者は現在のリポジトリ内で解決するかを見ており、後者は配布後の配置で解決するかを見ていた。**同じ項目でも、前提が変われば結論が変わる。**

`claude -p` を別プロセスで起動すれば、親セッションの文脈を持たない状態でレビューできる。Codex / Antigravity は別モデルであり、独立性はさらに高い。

### 外部送信に関する注意

**Tier 1 はレビュー対象の内容を外部サービスへ送信する。** Codex は OpenAI へ、Antigravity は Google へ、プロンプトに含めた内容がそのまま送信される。この事実を前提に、送信可否を毎回判断すること。

| 機密度 | 判断 |
|--------|------|
| 認証情報・個人情報・非公開の契約コード・顧客データを含む対象 | **Tier 1 を使わない。Tier 3（Claude Code 内の別視点）に限定する** |
| 該当するか判断がつかない | **安全側に倒し、Tier 3 を選ぶ** |
| 該当しないと確認できた対象 | Tier 1 を使ってよい |

実行前に必ず次を確認する。

- `.env` / シークレットファイル / `.gitignore` 済みファイルをプロンプトに含めない
- 導入先プロジェクトのセキュリティポリシー・秘密保持契約（NDA）を確認し、外部送信が許可されているかを確かめる
- 判断に迷う場合は Tier 3 を選ぶ（Tier 1 の速度・独立性より安全側を優先する）

### 実行経路の優先順位

```
Tier 1: CLI で実行（claude -p / codex / agy）          ← 原則これ
Tier 2: MCP 経由（CLI 未設定時のみ。Codex のみ対応）
Tier 3: Claude Code 内のペルソナで代替（最終手段）
```

**Antigravity は Tier 2（MCP）経路を持たない。** CLI が疎通しない場合、Tier 2 を飛ばして直接 Tier 3（Claude 別視点）へ移る。

手順の詳細は `.claude/skills/ai-cli-execution/SKILL.md` に従う。**CLI が使えるのに MCP や机上ペルソナを選ぶのは違反。**

**本ファイルと `.claude/docs/ai-cli-execution-policy.md` の住み分け**: 本ファイルは「視点＝誰がレビューするか」（レビュー文脈での視点定義・観点・裁定ルール）の正本。`ai-cli-execution-policy.md` は「ツールの担当領域・経路の実装」（Codex/Antigravity 呼び出しの経路実装、強みの割り当て、タイムアウト設計）の正本。レビューでの視点採否・観点割り当ては本ファイルに従い、CLI 呼び出しの実装詳細は `ai-cli-execution-policy.md` および `ai-cli-execution` スキルに従う。

### 実行時の既知の制約（実測、2026-08-16）

Tier 1 CLI を運用する上で実際に踏んだ制約。詳細手順は `.claude/skills/ai-cli-execution/reference.md` を正本とする（本節は再掲しない範囲で要点のみ記す）。

- `agy` はヘッドレス（`-p`）実行時、ファイル読み取り等のツール権限が自動拒否される。`--dangerously-skip-permissions` で回避すべきではない。対象ファイルの内容をプロンプトへ埋め込む方式を使う
- `agy --print-timeout` の既定は5分。長いレビューでは不足するため `15m` を指定する。値は単位付きの duration 文字列が必須で、単位なしの `900` は EXIT=2（オプション不正・空出力）になる
- `agy --output-format` は `text` / `json` / `stream-json` に対応する
- `codex exec` は trusted directory 外だと失敗する。プロンプトを引数で渡しても stdin を読もうとするため `< /dev/null` が必要
- `claude` の `--allowedTools`（許可リスト）と `--tools`（利用可能ツールの選択）は両方実在するが意味が異なる。読み取り専用レビューには `--allowedTools` が正しい

### 独立性の申告（必須）

全経路でレビュー結果の冒頭に次を記録する。

| 項目 | 記録内容 |
| --- | --- |
| 要求モデル | 依頼で指定したモデル識別子。指定なしの場合も明記 |
| 実行モデル | 実行ログ・ハーネス表示等で確認した識別子。不明なら「未確認」 |
| 根拠 | モデルを示すログ・セッション表示・出力メタデータの参照。CLIバージョンや自己申告だけで確定しない |
| 起動経路 | Tier、CLI/MCP/親内サブエージェント、独立プロセス・コンテキストの有無 |

Tier 3 では、呼出指定と登録定義の `model` が両方未指定なら `CLAUDE_CODE_SUBAGENT_MODEL` の既定が実行モデルを左右する。明示 `inherit`・FORCE・allowlistの例外を含む解決順はテンプレートリポジトリの agent-model-tuning.md（配布対象外）の前提を参照する。視点名だけで実行モデルを推定しない。

Tier 3 に落ちた場合は独立性の低下も必ず明示する。

```
Codex: 利用不可（CLI / MCP とも疎通せず）。Claude Code の別視点で代替したため、独立性は低下している。
```

黙って代替してはならない。読み手が結果の信頼度を判断できなくなる。

### 採用しない視点

**Cursor / Copilot は視点として使わない。** CLI を持たず机上ペルソナにならざるを得ないため、独立性が担保できない。エージェント定義（`.claude/agents/llm-personas/`）は他用途のために残置するが、本マトリクスの視点には含めない。

**Gemini は単体の机上ペルソナとしては使わない。** Gemini の推論能力は Antigravity CLI（`agy --model gemini-3.1-pro-high` 等）経由で利用する。「モデル名」（Gemini）と「実行環境＝視点」（Antigravity）は別物であり、混同しないこと。Antigravity という視点の内部でどのモデルを選ぶかは `ai-cli-execution-policy.md` §1 の担当領域定義に従う。

## 第2層: 観点（何を見るか）

9観点。**対象に応じて使うものを選ぶ**（全観点を常に使うわけではない）。

| # | 観点 | 見落とすと何が起きるか |
|---|------|---------------------|
| 1 | **要件充足** | 作ったが目的を満たしていない。「終わったつもり」 |
| 2 | **アーキテクチャ・構造** | 局所最適。拡張できない。依存が絡む |
| 3 | **実装品質・エッジケース** | 動かない。境界条件で壊れる |
| 4 | **セキュリティ** | 権限過剰、機密露出、脆弱性 |
| 5 | **UX・体験** | 使いにくい。導線が切れる。文言が伝わらない |
| 6 | **経営・事業** | 作る価値がない。コストが回収できない。収益導線が無い |
| 7 | **運用・保守** | 半年で陳腐化。障害時に手が出ない。属人化 |
| 8 | **ドキュメント・自己文書化** | 他人（未来の自分）が読めない |
| 9 | **規約・コンプライアンス** | 審査に落ちる。ライセンス違反。法規抵触 |

### 合議観点（複数視点が同じものを見る）

**観点 1・2・7 は、担当を割り振らず複数視点が重複して見る。**

重複はコストではなく**検出力**である。判定が割れること自体が情報であり、分担してしまうと片方の見落としがそのまま通過する。前掲のリンク欠陥は、2視点が同じ項目を見たために食い違いが顕在化して発見できた。

**コード実装では観点3・4（エッジケース・セキュリティ）も合議観点に加える。** 主担当を維持しつつ、他視点も同じ不変条件を破る反例を探す。コード以外では各スキルの対象別セットに従う。残りの観点は主担当の視点が強みを活かして見る。

**合議観点は、重複視点が実質1つしか稼働していない場合、単独視点扱いになる。** 稼働視点が縮退したときの扱いは「視点が縮退した場合の扱い」（裁定ルール節）を参照。その場合、レビュー結果にその観点が単独視点扱いであることを明記し、合議による検出力の向上（判定の割れの検出）は得られていない旨を示す。

### design-critique が単独実行のままである理由（判断・2026-08-20）

上表の「UI・画面・デザイン」行（Antigravity（主）/ Claude Code、観点1・5・8）は、UI・デザイン対象に3視点モデルを適用する場合の**参考の組み合わせ**として定義してあるが、2026-08-20 時点でこれを実際に呼び出すスキルは存在しない。UI・デザインレビューの実体は `design-critique` が単独で担う。2026-10-09 から共通前提のみを参照し、3視点モデルには接続しない。**単独実行は意図した設計であり、理由は次のとおり。**

| 理由 | 内容 |
|------|------|
| 実行基盤が異なる | `design-critique` は `execution_type: standalone`、`allowed-tools: Read, Grep, Glob` のみで Bash/Task を持たず、実CLI（`claude -p` / `codex` / `agy`）を別プロセスで起動できない。3視点モデルへ接続するには allowed-tools の拡張と execution_type の変更を伴う設計変更が必要で、境界明記の範囲を超える |
| 評価軸の性格が異なる | `design-critique` の4軸（ユーザビリティ・視覚階層・一貫性・アクセシビリティ）はUI/UXデザイン原則（WCAG・Gestalt等）に基づく専用軸であり、本正本の9観点（コード・スキル等の汎用成果物向け）に単純に1対1で写像できない |
| 用途が異なる | `design-critique` はモックアップ・スクリーンショット・実装途中の画面に対する**早期・単発**のフィードバックツールであり、code-review のようなマージ・リリースをブロックする正式ゲートではない。3視点合議のコストは早期フィードバックの速度と釣り合わない |

**この判断を覆す条件**: UI・画面変更に対して `code-review` 相当の正式な複数視点ゲート（マージ・リリースをブロックする判定）が必要になった場合は、`design-critique` を拡張するのではなく、上表「UI・画面・デザイン」行の組み合わせを使う新規スキル（または `code-review` の対象拡張）を検討する。`design-critique` 自体は早期フィードバック用途に留める。

## 機械検証との境界

**答えが一意に決まるものは視点に回さない。** スクリプトで1回検証すれば足り、複数視点で見ても同じ結果しか出ない。

| 判定 | 担当 | 例 |
|------|------|-----|
| 手続きで一意に決まる | `scripts/validate-structure.sh` / `self-check` スキル | frontmatter の具備、リンク文字列の実在、ファイルサイズ、byte-parity、命名規則 |
| 意味判断・外部知識が要る | 視点（LLM） | 発動キーワードの意味的衝突、設計の妥当性、外部バージョンの鮮度、情報設計 |

**機械側の検証条件は明示すること。** 前掲のリンク欠陥は「リンク文字列が実在するか」では検出できず、「**配布後の配置から解決するか**」という検証条件が必要だった。条件が曖昧なままスクリプト化すると同じ穴が残る。

## 裁定ルール（不一致の処理）

複数視点が同じ観点を見れば、判定は割れる。**割れた項目こそ最も情報量が多い。**

### 手順

```
Round 1: 各視点が独立にレビュー（合議観点は複数視点が見る）
Round 2: 不一致の抽出と裁定  ← ここが本体
Round 3: 統合レポート（一致項目 → 裁定結果 → 総合判定）
```

### 視点が縮退した場合の扱い

**稼働している視点が1つ以下の場合、Round 2（不一致の抽出と裁定）は成立しない。** 割れは比較対象が2つ以上あって初めて発生する。

対応:

- 稼働視点が1つの場合: Round 1 の単独結果のみを記録し、Round 2 は「実施不可（比較対象なし）」と明記する。総合判定は「保留」または「暫定」とする（後述）
- 稼働視点が0の場合: レビュー自体を実施不可としてエスカレーションする
- 合議観点（1・2・7）で重複視点が実質1つしか稼働していない場合、**その観点は単独視点扱いであると結果に明記する**
- 他視点が Tier 1/2/3 いずれかで復旧した後に再実行し、Round 2 以降を完成させる

### Round 2 の裁定

裁定者は**オーケストレーター（トップレベルの Claude Code セッション）**。

```
1. 同一項目で判定が割れたものを抽出する
2. 各視点が「何を前提に」その判定をしたかを読む
3. 一次情報に当たる（実ファイル / 実コマンドの実行 / 公式ドキュメント）
4. 事実で決着 → 採用。決着しない → 管理者へエスカレーション
```

**割れは次のどちらかを意味する。**

| 型 | 内容 | 対処 |
|---|------|------|
| (a) 前提の相違 | 両方が自分の前提の下で正しい | 前提を明示して両方採用。どの前提が実運用かを確定させる |
| (b) 一方の見落とし | 片方が誤り | 一次情報で確定させる |

### 禁止事項

- **多数決で潰さない。** 1対2でも少数側が正しいことがある（前掲のリンク欠陥は3視点中1視点のみが指摘した）
- **視点の権威づけをしない。** 「Claude Code が言っているから」で決めない
- **「たぶんこちら」で裁定しない。** 一次情報に当たれないなら、その旨を書いてエスカレーションする

### 管理者へのエスカレーション基準

一次情報で決着しないのは、事実問題ではなく**価値判断**の場合である。

| 条件 | 例 |
|------|-----|
| トレードオフの選択 | 厳密さと導入コストのどちらを取るか |
| 事業判断 | 課金導線の設計、料金体系、リリース時期 |
| 破壊的変更・不可逆 | 既存拠点への影響、削除、公開 |
| 前提そのものが未確定 | 「このプロジェクトは今後モバイルを持つのか」 |

## 総合判定

| 判定 | 条件 |
|------|------|
| **NG** | いずれかの観点が NG |
| **WARN** | NG なし、いずれかが WARN |
| **PASS** | 全観点 PASS |

裁定で決着しなかった項目が残る場合、総合判定は**保留**とし、エスカレーション先と待ち事項を明記する。「不明なので PASS」は禁止。

**稼働視点が1つ以下の場合、総合判定は原則「保留」または「暫定」とする。** 「暫定」は単独視点の結果のみで即応が必要な場合に限り使用し、他視点が復旧次第、必ず再実行して確定判定へ引き上げる旨を明記する。「稼働視点が足りないので PASS」は禁止。

この総合判定はAIレビューの検査範囲に対する判定であり、人間の承認・マージ許可ではない。機械検証の実施状態、人間の判断待ちは別に記録する。単独実行を前提とするスキルには、3視点モデルの縮退ルールを適用しない。

## 優先度の共通記法

各スキルは優先度の表記が異なる（`code-review`: `[MUST]` / `[SHOULD]` / `[NIT]` / `[Q]` / `[GOOD]`、`internal-structure-review`: P0 / P1 / P2 + OK / NG / 注意）。本正本では両者を対応させる共通尺度を定義する。**各スキル側の表記変更（追随）は別対応とし、本正本では定義のみ行う。**

| 共通尺度 | 意味 | `code-review` 表記 | `internal-structure-review` 表記 |
|---------|------|-------------------|----------------------------------|
| Critical | 対応必須。リリース・マージをブロックする | `[MUST]` | P0 / NG |
| Major | 対応が強く望ましい。次のイテレーションまでに解消する | `[SHOULD]` | P1 / 注意 |
| Minor | 細部の改善提案。任意対応 | `[NIT]` | P2 |
| Question | 判断材料が不足しており確認が必要 | `[Q]` | （エスカレーション扱い） |
| Positive | 良い実装・設計として明示的に評価する | `[GOOD]` | OK |

新規スキルが優先度記法を導入する際は、上表のいずれかにマッピングできる形にする（独自の尺度を追加する場合は本正本を先に更新する）。
